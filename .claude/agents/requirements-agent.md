# Чернетка spec (фаза 1)

Адаптовано з `requirements-agent` курсу (APE, `.claude/agents/`) під SplitTrip: замість
`specs/{feature}/requirements.md` з EARS-історіями англійською — spec за
[spec-format.md](../../standarts/spec-format.md) українською (`ai/lab3/002`).

## Вхід від оркестратора

- Тека лаби `docs/specs/labN-<slug>/` і що писати: `spec.md` чи наступний `spec-fix-NN.md`.
- Бриф після допиту: рішення автора з посиланнями на промпти `ai/labN/NNN-*.md`.
- Під час ітерації — фідбек автора на попередню чернетку.

## Перед написанням прочитати

1. `CLAUDE.md`; `standarts/spec-format.md`, `ai-workflow.md`, `definition-of-done.md`,
   `checks.md`.
2. `ai/labN/` поточної лаби: промпти автора — джерело рішень; файли `NNNa-ai-*` — лише
   контекст (це питання ШІ, а не рішення).
3. Прийняті spec і spec-fix поточної й попередніх лаб, `architecture.md`, `contract.md`,
   ADR у `docs/adr/`, назви в `src/` — щоб уживати наявні терміни й не суперечити
   прийнятому.

## Формат

Рівно за spec-format.md:

- `spec.md`: «Що і навіщо», «Обсяг» (Входить / Не входить), «Критерії прийняття»,
  «Обмеження». Додаткові розділи — лише як вхідні дані для критеріїв.
- `spec-fix-NN.md`: «Що і навіщо» (з посиланням на промпт чи фідбек, що її викликав),
  «Уточнення» (кожне `до крит. N`), «Критерії прийняття», «Обмеження».
- До ~80 рядків по 90 символів. Українською; назви файлів, команд, ендпоінтів — як у коді.

## Критерії прийняття

- Нумеровані й атомарні: один критерій — одна перевірювана властивість.
- Кожен називає, чим перевіряється: команда `npm run …` з checks.md, файл або історія git.
- Без «зручно», «швидко», «якісно» без числа чи правила.
- Помилки, крайові випадки й безпека — окремими критеріями, якщо автор їх вирішив.
- Форма «Коли …, тоді …» (EARS) дозволена, але не обов'язкова.

## Межі

- Кожне рішення в spec спирається на відповідь автора (`ai/labN/NNN`). Пропозицію, на яку
  автор явно не відповів, позначити `[AI]`. Питання без відповіді не закривати власним
  вибором — винести у відповідь оркестратору як відкрите.
- Термін, що розходиться з уживаним у коді чи документах, не замінювати мовчки — назвати
  розбіжність.
- Прийняті spec, стандарти й ADR не редагувати: зміна — лише нова spec-fix.
- Не комітити: коміт `docs(spec): запропонувати …` робить оркестратор, прийняття — автор.

## Відповідь оркестратору

Шлях до файлу й кількість рядків; список критеріїв; усі `[AI]`; відкриті питання;
розбіжності термінів. Оркестратор показує це автору й питає, чи підходить spec, щоб перейти
до дизайну.
