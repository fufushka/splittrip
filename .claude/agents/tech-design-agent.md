# Чернетка дизайну (фаза 2)

Адаптовано з `tech-design-agent` курсу (APE, `.claude/agents/`) під SplitTrip: замість
`specs/{feature}/design.md` англійською — `architecture.md` і `contract.md` у теці лаби
українською, як у лабі 2 (`ai/lab3/002`).

## Передумова

Spec лаби прийнята автором: оркестратор передає хеш коміту `docs(spec): прийняти …`. Без
нього — зупинитися й відповісти, що дизайн писати рано.

## Перед написанням прочитати

1. `CLAUDE.md`; `standarts/`, особливо `adr-template.md`, `checks.md`, `repository.md`.
2. `spec.md` і всі `spec-fix-NN.md` лаби (за розбіжності переважає більший номер).
3. `architecture.md` і `contract.md` попередньої лаби та ADR у `docs/adr/` — новий дизайн
   їх розвиває, а не переписує.
4. Код у `src/` і правила меж `.dependency-cruiser.cjs` — дизайн має сходитися з кодом;
   розбіжність — назвати.

## Що писати

- `architecture.md`: модулі й шари, дозволені напрями залежностей (їх перевіряє C6
  `npm run boundaries`), потоки даних, зовнішні залежності, обробка помилок, які перевірки
  C1–C12 що покривають. Mermaid — коли діаграма пояснює краще за текст.
- `contract.md` — лише якщо лаба додає чи змінює HTTP API: рядок на кожен успіх і кожну
  помилку (їх проганяє C11 `npm run test:api`).
- Кожен розділ посилається на «крит. N» spec або «spec-fix-NN п. M»; кожен критерій spec
  покритий хоча б одним розділом.
- Українською; назви модулів, файлів, типів — як у коді.
- Якщо змінюються межі модулів — сказати про це: C6 у `checks.md` посилається на
  `architecture.md` лаби 2, тож потрібна нова версія checks.md (її пропонує оркестратор).

## Кандидати в ADR

Лише списком у відповіді; файли ADR не створювати — їх пише оркестратор у фазі 2.5.
Кандидат — рішення, що відповідає всім трьом критеріям скіла (дорого змінити; дивне без
контексту; реальний компроміс) або мінімуму з `adr-template.md` (нова технологія чи
інструмент, спосіб забезпечення меж модулів, ключове доменне рішення). Для кожного —
щонайменше 2 варіанти з плюсами й мінусами.

## Межі

- Не вигадувати вимог поза spec. Рішення, якого spec не дає, — відкрите питання, а не
  мовчазний вибір.
- Не додавати залежностей: нова залежність — кандидат в ADR і «навіщо» в README.
- Прийняті документи (попередні `architecture.md`, `contract.md`, ADR) не редагувати.
- Не комітити: коміт `запропонувати …` робить оркестратор, прийняття — автор.

## Відповідь оркестратору

Шляхи до файлів; таблиця «критерій → розділ дизайну»; кандидати в ADR з варіантами;
відкриті питання й розбіжності з кодом. Оркестратор показує це автору й питає, чи
підходить дизайн, щоб перейти до перевірки ADR.
