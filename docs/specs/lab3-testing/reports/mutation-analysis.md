## 2. Вижилі мутанти

Причини класу «прийнятний»:

- **П1 — текст `detail` у `problem+json`.** contract.md, розд. 1 «Помилки», фіксує поля
  (`type`, `title`, `status`, `code`, `detail`, `requestId`) і `code` за таблицею, але не текст
  `detail`. Клієнт розрізняє помилки за `code`; тести перевіряють `code` і статус. Тест на
  дослівний текст ламався б від кожної правки формулювання, не захищаючи поведінку (див.
  спірне С4).
- **П2 — вміст логу.** Spec лаби 2, крит. 5–6, вимагає лише `processId` (і `userId`) у кожному
  рядку та відсутність секретів — це перевіряє `cross-cutting.test.ts` («логи (крит. 5, 6)»).
  Поля `tripId`, `op` і тексти повідомлень ні spec, ні contract.md не фіксують.
- **П3 — текст внутрішньої помилки.** Через HTTP недосяжна: суми й кількість часток
  обмежує схема (contract.md, розд. 1), а якби сталася — клієнт отримує `500` з фіксованим
  `detail` (`http/problems.ts:69`; contract: «500 без внутрішніх деталей»), текст іде лише
  в лог.

## 3. Топ-3 «реальна прогалина» (крит. 17)

Обрано за шкодою для користувача: по одному на гроші в розрахунку, гроші у витратах і
інваріант закритої поїздки. Коміт і статус «після» — після реалізації.

| № | Мутант | Тест (пропозиція) | Коміт | «Після» |
|---|---|---|---|---|
| 1 | #7 `balances/index.ts:84:5`, `creditor.amount -= amount` → `+=` | T1, unit | | |
| 2 | #36 `trips/domain.ts:134:57`, `e.id === expenseId ? next : e` → `true ? next : e` | T4, unit (або API) | | |
| 3 | #42 `trips/domain.ts:155:3`, `assertOpen(trip)` у `removeTransfer` → `;` | T5, unit (або API) | | |

1. **Пропозиції переказів платять не тому кредитору (#7).** Будь-яка поїздка, де більше
   заплатили двоє: напр. A платить 60 exact [C 30, D 30], B — 40 exact [C 20, D 20] →
   баланси A +60, B +40, C −50, D −50. `GET …/settlements` з мутантом: `C→A 50, D→A 50`.
   Хто виконає пропозиції, переплатить A на 40, B не отримає нічого, `close` → 409.
   Чинний тест «після переказів усі 0» має одного кредитора, тож властивість тримається.
   Головна обіцянка продукту («хто кому скільки») — і `balances` під `break` 100%.
2. **Редагування однієї витрати замінює всі (#36).** `PUT` однієї витрати переписує решту її
   копією з тим самим `id`: інші витрати зникають (адаптер Postgres за різницею агрегатів їх
   і видалив би), баланси хибні. Звичайна дія — виправити суму — тихо губить гроші. Тест PUT
   має одну витрату, де «замінити всі» = «замінити одну».
3. **Закрита поїздка змінюється через `DELETE` переказу (#42).** I4 «закрита поїздка не
   змінюється» порушено, і без вороття: після видалення баланси ≠ 0, а новий переказ у
   закриту поїздку → 409. Тест I4 обіцяє «кожна зміна → 409», але пропускає саме цей
   ендпоінт; забута перевірка в одній із семи операцій — найправдоподібніша з помилок.

Найближчі кандидати на заміну: #19 (I5: учасника однієї з кількох часток можна прибрати —
його борг зникає) і #26/#28/#29 (прибрати одного учасника — зникають усі або решта).

## 4. Коментарі `Stryker disable` (крит. 14; spec-fix-01, п. 3)

Еквівалентні знайдено лише в `balances`; у `money`, `trips/domain`, `trips/service`
коментарів не потрібно. Форма — рядком безпосередньо над мутованим виразом:

| Код | Де (рядок за звітом «до») | Коментар | Мутант |
|---|---|---|---|
| Д1 | над `const open = balances` (64) | `// Stryker disable next-line MethodExpression: еквівалентний — без filter нульові баланси потрапляють в open, але pick бере лише знак ±1, а order ненульових зберігає їхній відносний порядок` | #1 |
| Д2 | над `b.amount !== 0` усередині `.filter((b) => …)` (65) | `// Stryker disable next-line ConditionalExpression: еквівалентний — filter, що пропускає все, дає те саме, що й без filter (Д1)` | #2 |
| Д3 | над `x.order - y.order` усередині компаратора (74) | `// Stryker disable next-line ArithmeticOperator: еквівалентний — вхід sort іде за зростанням order, а V8 TimSort викликає компаратор як (пізніший, ранній), тож за рівних сум x.order + y.order > 0, як і x.order − y.order` | #6 |

- Stryker читає лише `leadingComments` вузла, і `next-line` діє на мутанти, що починаються
  на рядку цього вузла (`@stryker-mutator/instrumenter` 10.1.1, `directive-bookkeeper.js`).
  Коментар над рядком `.filter(` чи `.sort(` стає trailing-коментарем попередньої ланки
  ланцюжка й не діє — перевірено: #2 і #6 лишилися `Survived`.
- Д2 і Д3 Prettier переносить разом зі стрілкою на окремі рядки (лише пробіли). Після цього
  #5 (`|y| + |x|`) — на рядку вище Д3 і не ігнорується: його вбиває T2.
- Д2 ігнорує й варіант `(b) => false`, який зараз убито: у «після» на один killed менше,
  бал не змінюється.

## 7. Спірні випадки (рішення автора)

- **С1 — #6 еквівалентний лише на V8.** Із мутантом компаратор неузгоджений, а для такого
  ECMAScript лишає порядок на розсуд рушія; еквівалентність тримається на TimSort V8
  (Node ≥ 24, `engines`, ADR-0001). Альтернатива — прибрати зайвий тай-брейк
  `|| x.order - y.order` (`sort` стабільний з ES2019, вхід уже за `order`), але це зміна
  `src/`, тобто нова spec-fix.
- **С2 — #50, #51: прогалина чи прийнятний.** Через API різниці немає (обидва сховища
  сортують за `position`). Класифіковано як прогалину, бо порт `TripRepository` порядку не
  обіцяє, а `balancesOf` сортує саме для цього. Альтернатива — «прийнятний: стан недосяжний».
- **С3 — Д2, Д3 переносять код.** Коментар усередині виразу змушує Prettier розбити його на
  рядки (лише пробіли). Чи це в межах «`src/` змінюється лише коментарями» (spec-fix-01,
  «Обмеження»)?
- **С4 — П1 одним рядком.** Перевірка «`detail` — непорожній рядок» в `assertProblem`
  убила б 12 із 17 мутантів П1 (#10–12, 15, 24, 31, 33, 35, 39, 44, 52, 53), але не слова
  ролей (#30, 32, 34, 40, 41). contract.md непорожнього `detail` не вимагає — тому
  «прийнятний».
- **С5 — крит. 2 проти architecture.md, розд. 4.** Дизайн рахує 21/23 гілок на unit + API;
  для крит. 2 (самі unit) — 20/23, бо тай-брейк рядка 74 покривають лише API-тести. Закриває
  T1, зміни дизайну не потрібно.
