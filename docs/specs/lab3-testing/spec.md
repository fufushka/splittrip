# spec: Лаба 3 — тестування SplitTrip

Статус: прийнято (`011`). Вимоги — промпти автора [`ai/lab3/005–010`](../../../ai/lab3/),
питання AI — `006a`, `007a`, `009a`; `[AI]` — пропозиція AI без явної відповіді автора.

## Що і навіщо

Мета лаби — перевірити критичну логіку SplitTrip, перевірити взаємодію компонентів
інтеграційними тестами та налаштувати повний E2E-сценарій. Мутаційне тестування має
показати, які навмисні зміни в коді тести пропускають і де їх потрібно підсилити, щоб
вони виявляли реальні помилки (`009`).

## Обсяг

**Входить:** тести трьох рівнів, пороги покриття, `npm test`, мутації Stryker, аудит
топ-3 слабких тестів, DoD 0.3, checks.md 0.5, ADR, DEFENSE §5.
**Не входить:** CI (007, п. 9); мутації в `npm test` (007, п. 5) і поза модулями крит. 13
(007, п. 4); прямі тести адаптера `storage/postgres` (010, п. 4); зупинка Supabase після
прогону (007, п. 5); HTML-звіт Stryker у репо (008, п. 4); SQL-запити в E2E (008, п. 3).

## Рівні тестів (007, п. 1; 010, п. 3, 4)

**Unit** — модуль без справжніх зовнішніх залежностей (БД, Supabase); фейк у процесі тесту
дозволений, тож `test/unit/supabase-auth.test.ts` — unit (010, п. 3). **Інтеграційні** —
`app.inject` зі справжніми Postgres (`run_<id>`) і Supabase Auth: `npm run test:api:db`
(C12) — усі `test/api/*.test.ts`, зокрема `postgres.test.ts` (010, п. 4). API-тести на
`memory` (C11) лишаються в `npm run check`, але не інтеграційні. **E2E** — зібраний
`dist/main.js` окремим процесом на вільному порту, справжні БД і Auth, `fetch` по мережі.

## Критерії прийняття

1. **Рівні:** кожен рівень — окремий етап `npm test` із власним підсумком у виводі `[AI]`.
2. **Unit-модуль** (007, п. 2): самі unit-тести дають `balances` (`computeBalances`,
   `suggestTransfers`) 100% рядків і 100% гілок — звіт покриття `npm run test:unit`.
3. **Пороги покриття** (007, п. 3): гілки ≥ 90% на кожному з `money`, `balances`,
   `trips/domain`, `trips/service`, `idempotency` і 100% на `balances`; нижче → код ≠ 0.
4. **Вимір** (007, п. 3; 010, п. 1): вбудоване покриття Node; `npm test` — на unit +
   інтеграційних; `npm run check` і pre-push — на unit + API-тестах на `memory`.
5. **Поріг падає** (C10): `npm run demo` без Docker — прибраний тест валить поріг у check.
6. **`npm test`** (007, п. 5): перевірка Docker → `supabase start`, якщо не запущено →
   `run_<id>` і міграції → unit → інтеграційні → збірка й старт застосунку → етап E2E
   (крит. 9–12) → покриття з порогами крит. 3 → видалення бази й зупинка застосунку.
7. **Код виходу:** 0 — лише якщо пройшли всі етапи; без Docker — ненульовий ще до тестів.
8. **Прибирання:** база й застосунок прибираються й після падіння етапу `[AI]`.
9. **Етап E2E, повний шлях** (007, п. 6): `signup` → `login` → `POST /trips` → учасники →
   витрати → `GET /trips/:id/balances` → `GET /trips/:id/settlements` → перекази за
   пропозицією (`POST /trips/:id/transfers`) → баланси 0 → `POST /trips/:id/close` 200.
10. **Етап E2E, доступ:** чужа поїздка → `404`; refresh-токен після `logout` → `401`.
11. **Етап E2E, ідемпотентність** (008, п. 3): два `POST /trips/:id/expenses` з одним
    `Idempotency-Key` → однаковий `id`; `GET /trips/:id` показує одну витрату (лише API).
12. **Етап E2E, версія:** `GET /version` повертає sha `git rev-parse HEAD`.
13. **Мутації** (007, п. 4): `npm run mutation` — Stryker на `money`, `balances`,
    `trips/domain`, `trips/service` проти unit- і API-тестів на `memory`, без Docker.
14. **Поріг мутацій** (007, п. 4): `break` 100% лише на `balances` — налаштований до
    звіту «до» (010, п. 6); еквівалентні мутанти — коментар `Stryker disable` із причиною.
15. **Класифікація:** у `reports/mutation-analysis.md` для кожного вижилого мутанта —
    файл:рядок, зміна, причина й клас: реальна прогалина / еквівалентний / прийнятний.
16. **Звіти** (008, п. 4; 010, п. 6): вивід Stryker «до» і «після» — `.txt` у `reports/`,
    перший рядок — команда; код виходу: «до» — ненульовий, «після» — 0.
17. **Аудит топ-3:** для трьох мутантів класу «реальна прогалина» — тест, що вбиває
    мутант, окремим комітом `test: …` після звіту «до»; у `mutation-analysis.md` —
    мутант (файл:рядок, зміна) → тест → коміт; у звіті «після» вбитий (007, п. 7).
18. **DoD 0.3** (008, п. 2): правило DoD курсу §4 — AI оформлює spec лише з абзацу
    наміру автора й його відповідей; у «Лаба готова» — артефакти лаби 3.
19. **checks.md 0.5** (010, п. 1, 5): поріг покриття в check і pre-push; `npm test` і
    `npm run mutation` — вручну перед здачею, як C12 (007, п. 9), звіт у `reports/`.
20. **ADR** на ключові рішення (DoD); теми `[AI]`: Stryker і запуск тестів під ним,
    вбудоване покриття, оркестрація `npm test` і рівні тестів. README: «навіщо» Stryker.
21. **DEFENSE.md** (пише автор; 007, п. 8; README посилається): §2 — топ-3 розбіжностей
    «spec ↔ вихід AI»; §5 «Ефективність тестів» — mutation score до → після, топ-3
    слабких тестів → коміти, `npm run mutation`, посилання на `mutation-analysis.md`.
