# spec: Лаба 3 — тестування SplitTrip

Статус: чернетка. Вимоги — промпти автора [`ai/lab3/005–009`](../../../ai/lab3/): умова
лаби `005`, відповіді на допит `007`, `008` (питання — `006a`, `007a`), намір `009`.
Текст — чернетка AI; `[AI]` — пропозиція AI без явної відповіді автора.

## Що і навіщо

Мета лаби — перевірити критичну логіку SplitTrip, перевірити взаємодію компонентів
інтеграційними тестами та налаштувати повний E2E-сценарій. Мутаційне тестування має
показати, які навмисні зміни в коді тести пропускають і де їх потрібно підсилити, щоб
вони виявляли реальні помилки (`009`).

## Обсяг

**Входить:** тести трьох рівнів, пороги покриття, `npm test`, мутації Stryker, аудит
топ-3 слабких тестів, DoD 0.3, checks.md 0.5, ADR, DEFENSE §5.
**Не входить:** CI (007, п. 9); мутації в `npm test` (007, п. 5); мутації поза модулями
крит. 13, зокрема `storage/postgres`, `http`, `auth` (007, п. 4); зупинка Supabase після
прогону (007, п. 5); HTML-звіт Stryker у репо (008, п. 4); SQL-запити в E2E (008, п. 3).

## Рівні тестів (007, п. 1)

**Unit** — чистий модуль без I/O. **Інтеграційні** — застосунок у процесі тесту
(`app.inject`), справжні Postgres у базі `run_<id>` і локальний Supabase Auth: наявний
`npm run test:api:db` (C12) і тести адаптерів `storage/postgres`. API-тести на `memory`
(C11) лишаються в `npm run check`, але не інтеграційні. **E2E** — зібраний `dist/main.js`
окремим процесом на вільному порту, справжні БД і Auth, запити `fetch` по мережі.

## Критерії прийняття

1. **Рівні:** кожен рівень — окремий етап `npm test` із власним підсумком у виводі `[AI]`.
2. **Unit-модуль** (007, п. 2): unit-тести самі дають `balances` (`computeBalances`,
   `suggestTransfers`) 100% рядків і 100% гілок — звіт покриття `npm run test:unit`.
3. **Поріг покриття** (007, п. 3): `npm test` міряє покриття unit + інтеграційних тестів
   і завершується ненульовим кодом, якщо гілки < 90% на будь-якому з файлів `money`,
   `balances`, `trips/domain`, `trips/service`, `idempotency` або < 100% на `balances`.
4. **Інструмент:** вбудоване покриття Node, у `package.json` немає пакета покриття.
5. **Поріг падає** (C10): `npm run demo` — прибраний тест → поріг покриття відхиляє.
6. **Одна команда** (007, п. 5): `npm test` по черзі перевіряє Docker → `supabase start`,
   якщо не запущено → база `run_<id>` і міграції → unit → інтеграційні → збірка й старт
   застосунку → E2E → покриття з порогами крит. 3 → видалення бази й зупинка застосунку.
   Код 0 — лише якщо пройшли всі етапи.
7. **Без Docker** `npm test` завершується ненульовим кодом до запуску тестів.
8. **Прибирання:** база й застосунок прибираються й після падіння етапу `[AI]`.
9. **E2E, повний шлях** (007, п. 6): `signup` → `login` → `POST /trips` → учасники →
   витрати → `GET /trips/:id/balances` → `GET /trips/:id/settlements` → перекази за
   пропозицією (`POST /trips/:id/transfers`) → баланси 0 → `POST /trips/:id/close` 200.
10. **E2E, доступ:** другий користувач отримує `404` на чужу поїздку; після `logout`
    `POST /auth/refresh` зі старим refresh-токеном → `401`.
11. **E2E, ідемпотентність** (008, п. 3): два `POST /trips/:id/expenses` з одним
    `Idempotency-Key` → однаковий `id`; `GET /trips/:id` показує одну витрату (лише API).
12. **E2E, версія:** `GET /version` повертає sha `git rev-parse HEAD`.
13. **Мутації** (007, п. 4): `npm run mutation` — Stryker на `money`, `balances`,
    `trips/domain`, `trips/service` проти unit- і API-тестів на `memory`, без Docker.
14. **Поріг мутацій** (007, п. 4): `break` 100% лише на `balances`.
15. **Еквівалентні** мутанти — коментар `Stryker disable` із причиною (007, п. 4).
16. **Класифікація:** у `reports/mutation-analysis.md` для кожного вижилого мутанта —
    файл:рядок, зміна, причина й клас: реальна прогалина / еквівалентний / прийнятний.
17. **Звіти** (008, п. 4): вивід Stryker «до» і «після» — `.txt` у `reports/`, перший
    рядок — команда; HTML-звіт — у `.gitignore`.
18. **Аудит топ-3:** для трьох мутантів класу «реальна прогалина» — тест, що вбиває
    мутант, окремим комітом `test: …` після звіту «до»; у `mutation-analysis.md` —
    мутант (файл:рядок, зміна) → тест → коміт; у звіті «після» вбитий (007, п. 7).
19. **Hook-и** (007, п. 9): `npm run check` і pre-push запускають unit-тести з порогом
    покриття unit-рівня (`balances` 100%, крит. 2) `[AI]`; `npm test` — вручну, як C12.
20. **DoD 0.3** (008, п. 2): правило DoD курсу §4 — AI оформлює spec лише з абзацу
    наміру автора й його відповідей; у «Лаба готова» — артефакти лаби 3.
21. **checks.md 0.5** (007, п. 3, 5, 9) описує `npm test` і пороги покриття
    (крит. 3, 19): що перевіряє, як запустити, коли, що блокує.
22. **ADR** на ключові рішення (DoD); теми `[AI]`: Stryker і запуск тестів під ним,
    вбудоване покриття, оркестрація `npm test` і рівні тестів.
23. **Залежність:** README пояснює «навіщо» Stryker (DoD, «Коміт готовий»).
24. **README** посилається на DEFENSE лаби 3 (007, п. 8; DoD, «Лаба готова»).
25. **DEFENSE.md** (пише автор; 007, п. 8): §2 — топ-3 розбіжностей «spec ↔ вихід AI»;
    §5 «Ефективність тестів» — mutation score до → після, топ-3 слабких тестів → коміти,
    `npm run mutation`, посилання на `mutation-analysis.md`.
