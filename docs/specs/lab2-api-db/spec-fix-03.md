# spec-fix-03: Лаба 2 — безпека й передумови хмарного Supabase

Статус: прийнято (`ai/lab2/011`).

## Що і навіщо

Доповнює [spec.md](spec.md) і [contract.md](contract.md) перед прогоном у хмарі (крит. 11,
`ai/lab2/010`). Перевірка хмарного проєкту до міграцій показала дві речі, яких локальне
середовище не виявляє: Data API Supabase відкриває таблиці `public`, а проєкт вимагає
підтвердження email, яке контракт свідомо не підтримує.

## Уточнення

1. **До spec, «Не входить: RLS».** RLS як механізм доступу й далі поза обсягом: власника
   перевіряє сервіс `trips`. Але на кожній таблиці `public` RLS **увімкнено без політик**
   (міграція `0002`): інакше Data API Supabase з публічним publishable-ключем дає читати й
   змінювати поїздки напряму, в обхід API. Застосунок підключається роллю власника таблиць
   і RLS обходить.
2. **До spec, «Не входить: підтвердження email».** Передумова середовища: у проєкті Supabase
   вимкнено «Confirm email» (локально — `enable_confirmations = false`). Якщо підтвердження
   увімкнено, `POST /auth/signup` повертає `500` з причиною в лозі, а не «успіх без токенів».

## Критерії прийняття

- П. 1: тест БД — у схемі `public` немає таблиць без RLS; у хмарі після `db:migrate` —
  запит до `<SUPABASE_URL>/rest/v1/trips` з publishable-ключем не повертає рядків.
- П. 2: модульний тест адаптера — відповідь signup без сесії дає помилку з причиною
  «Confirm email»; README описує передумову.
