# spec-fix-02: Лаба 2 — уточнення етапу БД

Статус: прийнято (`ai/lab2/010`).

## Що і навіщо

Доповнює [contract.md](contract.md) і [spec-fix-01](spec-fix-01.md). Під час переходу на
Postgres (`ai/lab2/009`) AI знайшов місця, де прийнятий контракт неповний або суперечить
сам собі: схема не дозволяла виразити I3 для часток, порядок часток залежав від сховища,
а поведінку refresh-токена контракт не визначав.

## Уточнення

1. **До contract.md, розд. 2, `expense_shares`.** Таблиця має ще колонку `trip_id`. Без неї
   складений FK `(trip_id, participant_id)` неможливий, і I3 для учасників поділу тримається
   лише в домені, хоча контракт обіцяє його й у БД. Каскадне видалення — через FK
   `(trip_id, expense_id) → expenses`.
2. **До contract.md, розд. 1, `split`.** Частки у відповіді завжди впорядковані за порядком
   додавання учасника (`position`) — і для `equal`, і для `exact`. Раніше `exact` повертав
   порядок запиту в memory, а БД порядку запиту не зберігає: одна й та сама витрата
   виглядала по-різному залежно від `STORAGE`.
3. **До contract.md, розд. 1, `/auth/refresh` `[AI]`.** Новий refresh-токен видається на
   кожен `refresh`; старий **може** діяти ще до 10 с (`refresh_token_reuse_interval`
   Supabase — захист паралельних запитів клієнта). Гарантовано: після `logout` refresh-токен
   не діє (spec, крит. 6). Одноразовість старого токена контракт не обіцяє.

## Критерії прийняття

- П. 1: `db/migrations/0001-init.sql` — `expense_shares.trip_id` і FK; тест БД: частка з
  учасником іншої поїздки відхиляється з `23503` в обхід домену.
- П. 2: `npm run test:api` і `npm run test:api:db` — однакові відповіді для `exact`-поділу.
- П. 3: API-тести не перевіряють одноразовість старого refresh-токена; тест після `logout`
  лишається.

## Обмеження

Ті самі, що в spec.md.
