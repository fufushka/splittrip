# spec-fix-04: Лаба 2 — виправлення за незалежним рев'ю

Статус: прийнято (`ai/lab2/014`).

## Що і навіщо

Доповнює [contract.md](contract.md), [spec-fix-01](spec-fix-01.md) і ADR-0019. Незалежне
рев'ю коду сабагентом зі свіжим контекстом (`ai/lab2/012`) знайшло дефекти; автор
підтвердив головний і вирішив виправити всі (`ai/lab2/013`): «якщо поділити 1 копійку на 2,
то запит прийде 201, а Postgres падає з 500 — це бага».

## Уточнення

1. **До крит. I6 / contract.md, `split.mode = equal` (автор, 013).** Кожна частка — ≥ 1
   копійка. Сума, менша за кількість учасників поділу, → `422 share_too_small`, однаково на
   memory і Postgres. Раніше memory зберігав частку 0 (`201`), а БД відхиляла її `check`
   (`500`).
2. **До ADR-0019, п. 2.** Помилка збереження відповіді після вже виконаної операції не
   змінює відповідь клієнту: логується (`error`), клієнт отримує оригінальний статус і тіло.
   Раніше `201` перетворювався на `503`, хоча зміну збережено.
3. **До ADR-0019, п. 1 `[AI]`.** Ключ у стані «обробляється», старший за 60 с, вважається
   покинутим: `reserve` його перезаймає. Раніше повтор отримував `409` до 24 год.
4. **До ADR-0018, ретраї `[AI]`.** Повтор транзакції після обриву з'єднання на `COMMIT`
   (результат невідомий) не дає `500`: `create` поїздки — `insert … on conflict (id) do
   nothing`, якщо рядок з тим самим `id` належить тому самому власнику.
5. **До ADR-0017 `[AI]`.** Supabase Auth: `429` → `503` з `Retry-After`; не-JSON тіло
   відповіді чи обрив під час читання → `503`, а не `500` / `401`.
6. **До spec, «Збої» `[AI]`.** `/ready` відповідає не довше за 2 с: БД, що не відповідає,
   → `503`, а не завислий запит.

## Критерії прийняття

- П. 1: API-тест (memory і Postgres): `amount: 1` на двох → `422 share_too_small`;
  `amount: 2` на двох → `201`, частки `[1, 1]`.
- П. 2–3: API-тести: збій `complete` після успіху → оригінальний `201`; паралельний дубль
  ключа → `409 idempotency_in_progress` (ADR-0019, «Підтвердження»); `5xx` звільняє ключ;
  «завислий» ключ старший за 60 с перезаймається.
- П. 4: тест БД: повторне `create` з тим самим `id` і власником — без помилки, один рядок.
- П. 5: модульні тести адаптера: `429` і не-JSON → `AuthUnavailableError`.
- П. 6: тест БД: `/ready` через «завислий» проксі відповідає `503` за ≤ 3 с.
- Мутаційна перевірка: прибрати кожне виправлення → відповідний тест падає.

## Обмеження

Ті самі, що в spec.md. Виправлення — лише після коміту прийняття цієї spec-fix
(ai-workflow 0.4, якщо її прийнято).
