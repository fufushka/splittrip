# spec: Лаба 1 — фундамент і структура SplitTrip

## Що і навіщо

**SplitTrip** — сервіс для спільних витрат у подорожі: учасники записують, хто за що
заплатив і за кого, а сервіс рахує баланси й пропонує перекази для розрахунку.
Мета лаби — закласти проєкт, стандарти й конвеєр перевірок на весь курс; межі модулів
виводяться з функціоналу й даних, а не з обраних інструментів.

## Функціонал продукту (вхід для проєктування; реалізація — з лаби 2)

- Створити поїздку; додати й прибрати учасників.
- Записати витрату: хто заплатив, скільки, між ким і як ділиться.
- Змінити або видалити витрату.
- Переглянути баланс кожного учасника.
- Отримати запропоновані перекази для повного розрахунку.
- Зафіксувати переказ між учасниками.
- Закрити поїздку, коли всі розрахувалися.

## Обсяг

**Входить:** README з ідеєю; пакети, стиль коду, форматер, лінтер, статичний аналіз;
перевірки перед комітом і пушем; smoke-тест; стандарти; архітектура; ADR; каркас
модулів без бізнес-логіки; аудит; DEFENSE.md.
**Не входить:** функціонал, зберігання даних, автентифікація, UI, CI, деплой.

## Критерії прийняття

Кожен критерій перевіряється командою, файлом або історією git.

**Проєктування (до реалізації)**
1. **Стандарти.** `standards/`: формат spec, шаблон ADR (MADR), власний DoD, перелік
   перевірок (що, як запустити, коли, що блокує), правила роботи з ШІ.
2. **Архітектура.** `architecture.md` поруч зі spec: модулі, їхня взаємодія й
   обґрунтування меж; правила залежностей; дані та зв'язки (ER); як змінюються дані
   в кожному сценарії «Функціоналу продукту» — жоден не пропущено.
3. **ADR** (контекст, альтернативи, рішення, наслідки) на кожне ключове рішення — з
   реальними альтернативами або дороге для зміни. Мінімум: кожна технологія чи
   інструмент; спосіб забезпечення меж модулів; ключові доменні рішення з архітектури.
4. **Порядок.** Коміти стандартів, архітектури й ADR — раніше за перший коміт реалізації.

**Конвеєр**
5. **Відтворюваність.** На чистому клоні одна команда `make …` запускає всі перевірки
   (формат, лінт, статичний аналіз, межі модулів, збірка, smoke) і вони проходять; як —
   описано в README.
6. **Автопідключення.** Перевірки перед комітом і пушем підключаються під час
   встановлення проєкту, без ручних кроків.
7. **Брудний коміт блокується.** Порушення стилю чи лінту відхиляє коміт; зламана
   збірка чи smoke відхиляє пуш. Реальний вивід обох відмов збережено у звіті.
8. **Smoke-тест.** Застосунок стартує, відповідає на перевірку стану й повертає версію —
   ідентифікатор поточного коміту, а якщо його не визначити — явне «невідомо», не помилку.

**Структура**
9. **Структура = архітектура.** Кожен модуль з `architecture.md` — окремий модуль у коді
   з однією публічною точкою входу. Інших доменних модулів немає.
10. **Межі — автоматично.** Обхід точки входу, цикл або заборонений напрям залежності
    валить перевірки. Демонстрацію збережено у звіті.

**Репозиторій і здача**
11. **Чистий репозиторій:** без встановлених залежностей, артефактів збірки, секретів;
    файли без розширення — лише з дозволеного списку в стандартах.
12. **Слід ШІ.** Кожен промпт — в `ai/` з посиланням на породжені коміти; коміти ШІ
    позначено за стандартами.
13. **Аудит** — окремий звіт: (а) кожен критерій — виконано чи ні + доказ; (б) топ-3 зайві
    або неправильні залежності з рішенням; (в) топ-3 «зрізані кути» ШІ проти spec:
    промпт → фідбек → правка spec чи стандарту → коміт виправлення.
14. **DEFENSE.md** — за шаблоном курсу, не більше 1 сторінки.
15. **Процес.** feature-branch → PR з рев'ю-коментарями → merge; коміти — за стандартами,
    один логічний крок на коміт.

## Обмеження

- Spec, стандарти й ADR: ШІ пропонує чернетку, автор приймає окремим комітом (правки або
  статус «прийнято»). Після прийняття ШІ їх не змінює.
- Розбіжність виправляється зміною spec, стандарту або додатковою spec, не ручним патчем коду.
- Кожна залежність має однорядкове «навіщо» в README.
- Якщо spec неоднозначна, ШІ зупиняється й питає.
