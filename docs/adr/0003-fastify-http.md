# 0003. Fastify 5 як HTTP-фреймворк

## Контекст і проблема

Застосунок — HTTP-сервіс: у лабі 1 лише `GET /health` і `GET /version` (spec-fix-01, п. 1),
з лаби 2 — API поїздок, витрат і переказів із валідацією вхідних даних.

## Чинники рішення

- Валідація тіла запиту й відповіді без окремої бібліотеки.
- Типи для TypeScript без ручних оголошень.
- Вбудоване логування.
- Доменні модулі не повинні залежати від фреймворку (архітектура, ADR-0006).

## Розглянуті варіанти

- Fastify 5
- Express 5
- Hono
- Вбудований `node:http`

## Рішення

Обрано «Fastify 5», бо він дає валідацію через JSON Schema, логер pino і типи з коробки.
HTTP лишається адаптером: доменні модулі його не імпортують, тож заміна фреймворку
торкнеться лише HTTP-шару.

### Наслідки

- Добре: менше власного коду для валідації й серіалізації.
- Погано: менше прикладів і довідок, ніж для Express; інша модель плагінів.

### Підтвердження

Лише HTTP-шар імпортує `fastify` — правило dependency-cruiser (ADR-0006, `make boundaries`).
Smoke-тест проходить на зібраному застосунку (`make smoke`).

## Плюси й мінуси варіантів

### Fastify 5

- Добре: схеми, pino, типи, швидкодія.
- Погано: трохи вищий поріг входу.

### Express 5

- Добре: найвідоміший, багато матеріалів.
- Погано: валідація й типізація — окремими бібліотеками й власним кодом.

### Hono

- Добре: легкий, сучасний, добрі типи.
- Погано: орієнтований на edge-рантайми; для Node-сервера переваг немає.

### `node:http`

- Добре: нуль залежностей.
- Погано: маршрутизацію, валідацію, розбір JSON писати самим — з лаби 2 це зайвий код.
