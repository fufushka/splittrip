# 0015. Postgres (Supabase) через postgres.js, без ORM

## Контекст і проблема

Лаба 2 замінює статичні дані на БД з транзакціями, `SELECT … FOR UPDATE` і ретраями
(spec, «Збої»; contract.md, розд. 2). Автор обрав Supabase (`ai/lab2/003`) і підключення
через Supavisor (`ai/lab2/004`). Треба обрати спосіб доступу до БД з Node.

## Чинники рішення

- Транзакції й блокування рядків — обов'язкові (spec, крит. 7).
- SQL лише в `storage`; сирий SQL — через tagged templates (рекомендація лаби), без
  конкатенації рядків.
- Точний контроль кількості запитів для агрегату (крит. 10, N+1).
- Робота через Supavisor у transaction mode (без prepared statements).
- Мінімум залежностей і магії; домен не знає про БД.

## Розглянуті варіанти

- postgres.js (tagged templates, власний пул)
- `@supabase/supabase-js` (PostgREST поверх HTTP)
- Kysely (типізований query builder) поверх `pg`
- Drizzle ORM
- `pg` + `sql-template-tag`

## Рішення

Обрано **postgres.js**: tagged template `` sql`… ${x}` `` параметризує значення, пул і
`sql.begin()` для транзакцій вбудовані, `prepare: false` вмикає сумісність із Supavisor
transaction mode. Моделі — TypeScript-типи домену в `trips`; рядки БД відображаються в них
лише в `storage` (одна стратегія розміщення моделей). Суми — `bigint` у БД, у коді —
`number` цілих копійок (`≤ 10¹⁰` < `Number.MAX_SAFE_INTEGER`, contract.md).

### Наслідки

- Добре: SQL видно як є — легко перевірити `FOR UPDATE`, пакетні вставки й кількість запитів.
- Добре: одна runtime-залежність без кодогенерації й CLI.
- Погано: типи результатів запитів пишемо вручну; помилку в назві колонки ловить лише тест
  на реальній БД (`npm run test:api:db`), не `tsc`.
- Погано: міграції — окремо (ADR-0020), драйвер їх не дає.

### Підтвердження

C6: `postgres` імпортується лише в `src/modules/storage/` (dependency-cruiser);
`npm run test:api:db` проходить на локальному Supabase; ESLint і рев'ю — без конкатенації в SQL.

## Плюси й мінуси варіантів

### postgres.js

- Добре: tagged templates, транзакції, пул, швидкий; підтримка `prepare: false`.
- Погано: ручні типи рядків.

### supabase-js

- Добре: офіційний клієнт Supabase, той самий ключ для Auth.
- Погано: **немає транзакцій** і `FOR UPDATE` — PostgREST виконує один запит на HTTP-виклик;
  вимогу лаби не виконати.

### Kysely

- Добре: типобезпечні запити, автодоповнення колонок.
- Погано: власний DSL замість SQL; ще генератор типів зі схеми; більше коду для рев'ю.

### Drizzle ORM

- Добре: схема в TypeScript, міграції з коробки.
- Погано: моделі прив'язані до ORM, а не до домену; приховує кількість запитів
  (`with`-зв'язки), що ускладнює контроль N+1.

### pg + sql-template-tag

- Добре: найпоширеніший драйвер.
- Погано: дві залежності замість однієї; транзакції й ретраї — вручну через `client`.
