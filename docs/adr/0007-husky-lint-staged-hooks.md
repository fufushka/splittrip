# 0007. husky + lint-staged для git-hook-ів, власні скрипти для повідомлень і чистоти репо

## Контекст і проблема

Hook-и мають підключатися під час встановлення без ручних кроків (spec.md, крит. 6),
блокувати коміт із порушенням формату чи лінту, а пуш — зі зламаною збіркою чи smoke
(крит. 7). Також потрібні перевірки повідомлення коміту (C4) і чистоти репо (C3).

## Чинники рішення

- Автопідключення через `npm ci` / `npm install`.
- Перевіряти вміст, що комітиться, а не робочу копію.
- Власне правило: файл із трейлера `AI-Prompt` має існувати (standarts/ai-workflow.md).
- Жодних бінарників, які треба встановлювати вручну.

## Розглянуті варіанти

- husky + lint-staged; C3 і C4 — власні Node-скрипти в `scripts/`
- lefthook
- Власний каталог `.githooks/` + `git config core.hooksPath` у `prepare`
- commitlint для C4, gitleaks для секретів

## Рішення

Обрано «husky + lint-staged + власні скрипти».

- husky підключається скриптом `prepare` і сам пропускає ситуацію без `.git`. Hook-и лежать
  у `.husky/`: `pre-commit`, `commit-msg`, `pre-push`. Це каталог hook-ів для
  standarts/repository.md.
- lint-staged запускає Prettier і ESLint лише на доданих до коміту файлах — так перевіряється
  саме те, що потрапить в історію.
- C4 (`scripts/check-commit-msg.ts`) і C3 (`scripts/check-hygiene.ts`) — власні, бо commitlint
  не перевіряє наш трейлер, а gitleaks — окремий бінарник (ручне встановлення).
- Hook-и викликають лише цілі `make` (standarts/checks.md).

### Наслідки

- Добре: `npm ci` = готові hook-и; перевіряється вміст коміту.
- Погано: пошук секретів у C3 базовий (шаблони й імена файлів) — слабший за gitleaks.
- Погано: власні скрипти треба підтримувати й тестувати самим.

### Підтвердження

На чистому клоні після `make install` `git config core.hooksPath` = `.husky/_`; брудний коміт
і пуш зі зламаною збіркою відхиляються — вивід у `reports/` (крит. 7).

## Плюси й мінуси варіантів

### husky + lint-staged + власні скрипти

- Добре: де-факто стандарт; перевірка доданого вмісту; наші правила — нашим кодом.
- Погано: дві залежності плюс власні скрипти.

### lefthook

- Добре: швидкий, паралельний, один конфіг.
- Погано: Go-бінарник через npm-обгортку; менш поширений.

### `.githooks/` + `core.hooksPath`

- Добре: нуль залежностей.
- Погано: `prepare` падає без `.git`; перевірку лише доданих файлів треба писати самим.

### commitlint + gitleaks

- Добре: зрілі інструменти.
- Погано: commitlint не знає нашого трейлера; gitleaks вимагає ручного встановлення.
