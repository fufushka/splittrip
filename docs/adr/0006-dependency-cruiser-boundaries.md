# 0006. dependency-cruiser для автоматичних меж модулів

## Контекст і проблема

Кожен модуль з `architecture.md` має одну публічну точку входу; звернення в обхід неї,
цикл або заборонений напрям залежності мають валити перевірки (spec.md, крит. 9, 10;
перевірка C6).

## Чинники рішення

- Одним інструментом покрити всі три порушення: обхід точки входу, цикли, напрям.
- Правила — декларативно, поруч з архітектурою, щоб їх можна було звірити.
- Демонстрація порушення має бути відтворюваною для звіту.

## Розглянуті варіанти

- dependency-cruiser
- eslint-plugin-boundaries + `import/no-cycle`
- npm workspaces: кожен модуль — окремий пакет з `exports`
- ESLint `no-restricted-imports`

## Рішення

Обрано «dependency-cruiser», бо він з коробки має правила для циклів (`no-circular`), для
напрямів між шляхами (`from`/`to`) і для імпорту в обхід `index.ts`. Крім того, він будує
граф модулів у Mermaid для `architecture.md` і аудиту.

### Наслідки

- Добре: одна конфігурація `.dependency-cruiser.cjs` = машинно-перевірювані правила
  з `architecture.md`.
- Добре: правило `no-non-package-json` компенсує «підняття» пакетів у npm (ADR-0002).
- Погано: окремий від ESLint інструмент і окремий крок у `make check`.

### Підтвердження

`make boundaries` (C6) проходить; навмисне порушення кожного з трьох типів валить
перевірку — вивід у `reports/` (крит. 10).

## Плюси й мінуси варіантів

### dependency-cruiser

- Добре: цикли, напрями, точки входу, граф — в одному.
- Погано: ще одна конфігурація.

### eslint-plugin-boundaries + `import/no-cycle`

- Добре: помилки прямо в редакторі.
- Погано: `import/no-cycle` повільний; два плагіни замість одного правила.

### npm workspaces з `exports`

- Добре: точку входу гарантує сам Node.
- Погано: npm піднімає пакети, тож напрям залежностей не контролюється; цикли між
  пакетами не ловляться; багато `package.json` для маленького проєкту.

### `no-restricted-imports`

- Добре: без нових залежностей.
- Погано: не ловить цикли; правила на кожен модуль писати вручну.
