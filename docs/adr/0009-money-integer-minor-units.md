# 0009. Гроші — цілі числа в мінімальних одиницях

## Контекст і проблема

Баланси мають сходитися до копійки, а закриття поїздки вимагає балансу рівно 0
(spec-fix-02). У JavaScript `0.1 + 0.2 !== 0.3`, тож дробові числа для грошей дають
«залишкові» копійки й поїздку, яку неможливо закрити (spec-fix-03, п. 1).

## Чинники рішення

- Точна арифметика додавання й віднімання.
- Точне порівняння з нулем.
- Простота: без зовнішніх бібліотек у домені (architecture.md, правило 4).

## Розглянуті варіанти

- `number` із цілими копійками, перевірка `Number.isSafeInteger`
- `bigint` із копійками
- Десяткова бібліотека (decimal.js, dinero.js)
- `number` із гривнями (дробові)

## Рішення

Обрано «`number` із цілими копійками»: брендований тип `Money` у модулі `money`, будь-яке
значення перевіряється `Number.isSafeInteger`. Безпечна межа — ≈ 9·10¹³ грн, цього досить.
Множення й ділення грошей у домені лише через `allocateEqually` (ADR-0010).

### Наслідки

- Добре: точність, звичайні оператори, серіалізація в JSON без перетворень.
- Погано: API приймає й віддає копійки; перетворення в «грн, коп.» — задача клієнта.
- Погано: припущення, що валюта має 2 знаки після коми, зафіксоване в документації
  API, а не в коді.

### Підтвердження

Модульні тести `money` (з лаби 2): відмова для дробових і небезпечних значень;
`Money` — брендований тип, тож звичайне `number` не передати без перевірки (`make typecheck`).

## Плюси й мінуси варіантів

### `number` із копійками

- Добре: просто й точно в межах `MAX_SAFE_INTEGER`.
- Погано: межу треба перевіряти явно.

### `bigint`

- Добре: без верхньої межі.
- Погано: не серіалізується в JSON напряму; змішування з `number` кидає помилку.

### Десяткова бібліотека

- Добре: готові округлення й валюти.
- Погано: зовнішня залежність у домені; для додавання цілих — зайве.

### `number` із гривнями

- Добре: «природні» числа в API.
- Погано: помилки округлення — баланс не дорівнює 0 рівно.
