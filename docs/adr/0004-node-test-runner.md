# 0004. `node:test` для тестів і smoke-тесту

## Контекст і проблема

Потрібен smoke-тест, який доводить, що застосунок стартує й відповідає на `/health` та
`/version` (spec.md, крит. 8; spec-fix-01, п. 1), а з лаби 2 — модульні тести домену.

## Чинники рішення

- Smoke має перевіряти реальний запуск, а не виклик у пам'яті.
- Мінімум залежностей.
- Запуск `.ts` без окремої збірки (ADR-0001).

## Розглянуті варіанти

- Вбудований `node:test` + `node:assert`
- Vitest
- Jest

## Рішення

Обрано «`node:test`», бо він вбудований у Node 24, запускає `.ts` напряму й має все
потрібне: `describe/it`, моки, вивід TAP/spec, покриття.

Smoke-тест запускає зібраний `dist/` окремим процесом на випадковому порту, чекає на
`/health`, перевіряє `/version` і зупиняє процес. `fastify.inject()` не використовується,
бо він не доводить, що процес стартує.

### Наслідки

- Добре: нуль залежностей для тестування.
- Погано: менш зручний режим спостереження й звіти, ніж у Vitest; менше матчерів.

### Підтвердження

`make smoke` (C8) запускає тест на зібраному застосунку; у `package.json` немає
тестового фреймворку.

## Плюси й мінуси варіантів

### `node:test`

- Добре: вбудований, швидкий, без конфігурації.
- Погано: скромніший DX.

### Vitest

- Добре: зручний watch, багаті матчери, звіти.
- Погано: окрема залежність без потреби, якої не закриває `node:test`.

### Jest

- Добре: відомий.
- Погано: складна підтримка ESM і TypeScript — потрібні трансформери.
