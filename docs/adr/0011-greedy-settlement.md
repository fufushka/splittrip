# 0011. Жадібний алгоритм пропонованих переказів

## Контекст і проблема

Сервіс пропонує перекази, після яких баланс кожного = 0 (spec-fix-02). Бажано, щоб
переказів було мало (spec-fix-03, п. 7).

## Чинники рішення

- Після виконання всіх пропозицій кожен баланс = 0.
- Мало переказів; не більше n − 1 для n учасників з ненульовим балансом.
- Детермінований результат і час O(n log n).

## Розглянуті варіанти

- Жадібний: найбільший боржник платить найбільшому кредитору
- Точний мінімум переказів (перебір підмножин із нульовою сумою)
- Попарний: кожен боржник платить кожному кредитору пропорційно
- Переказ лише через одного «банкіра»

## Рішення

Обрано «жадібний»: сортуємо боржників і кредиторів за модулем балансу (за рівності —
за `position`), створюємо переказ на `min(|борг|, кредит)` і повторюємо, доки всі баланси
не стануть 0. Кожен крок обнуляє щонайменше одного учасника, тож переказів ≤ n − 1.

### Наслідки

- Добре: просто, швидко, детерміновано, завжди обнуляє баланси.
- Погано: не завжди дає абсолютний мінімум (точний мінімум — NP-складна задача); для
  типової поїздки різниця — 0–1 переказ.

### Підтвердження

Модульні тести `suggestTransfers` (з лаби 2): після застосування пропозицій усі баланси = 0;
кількість ≤ n − 1; той самий вхід — той самий результат.

## Плюси й мінуси варіантів

### Жадібний

- Добре: O(n log n), ≤ n − 1 переказ.
- Погано: не гарантує глобальний мінімум.

### Точний мінімум

- Добре: найменше можливе число переказів.
- Погано: експоненційний час; складно пояснити й протестувати.

### Попарний пропорційний

- Добре: «справедливий» розподіл.
- Погано: до k·m переказів і дробові копійки.

### Через «банкіра»

- Добре: тривіально.
- Погано: до 2(n − 1) переказів; навантажує одну людину.
