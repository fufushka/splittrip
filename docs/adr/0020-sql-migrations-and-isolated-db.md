# 0020. Міграції — SQL-файли з власним раннером; окрема база на кожен прогін

## Контекст і проблема

Схема з contract.md має накочуватися відтворювано на локальний Supabase (Docker + Supabase
CLI, `ai/lab2/004`) і на хмарний проєкт. Рекомендація лаби — ізольоване середовище: не
спільні 5432–5434 на localhost, окрема база на прогін або гілку.

## Чинники рішення

- Одна команда накочує схему на будь-яку базу за `DATABASE_URL`.
- Кожен прогін тестів — у власній базі, паралельні прогони не заважають один одному.
- Міграція не редагується після застосування (як прийнята spec).

## Розглянуті варіанти

- Власний раннер `db/migrations/NNNN-*.sql` + таблиця `schema_migrations`
- Supabase CLI migrations (`supabase/migrations`, `supabase db reset`)
- node-pg-migrate

## Рішення

Обрано **власний раннер** (`npm run db:migrate`, ~50 рядків, postgres.js):

- файли `db/migrations/NNNN-<назва>.sql` застосовуються за номером, кожен у транзакції;
- у `schema_migrations` — ім'я й SHA-256 файлу; змінений застосований файл → помилка.

Ізоляція: Supabase CLI (`npx supabase start`) піднімає Postgres на `54322`.
`npm run test:api:db` створює базу `run_<uuid>`, мігрує її, проганяє API-тести й видаляє
базу навіть після падіння. Хмара — той самий раннер через Supavisor.

### Наслідки

- Добре: одна команда для будь-якої бази; база на прогін створюється за секунди.
- Добре: перевірка хешу ловить редагування вже застосованої міграції.
- Погано: немає `down`-міграцій; відкат — нова міграція.
- Погано: схема `auth` є лише в базі `postgres`, тож `owner_id` — без FK на `auth.users`
  (contract.md).

### Підтвердження

Крит. 2: `npm run test:api:db` створює й видаляє `run_<id>`; повторний `db:migrate` нічого не
застосовує; змінений застосований файл → ненульовий код виходу.

## Плюси й мінуси варіантів

### Власний раннер

- Добре: працює з будь-якою базою; без нових залежностей.
- Погано: свій код, який треба тестувати.

### Supabase CLI migrations

- Добре: офіційний шлях Supabase.
- Погано: застосовується до бази `postgres` проєкту, а не до довільної `run_<id>`.

### node-pg-migrate

- Добре: зрілий інструмент, `down`-міграції.
- Погано: залежність від `pg` поруч із postgres.js; JS-DSL замість SQL.
