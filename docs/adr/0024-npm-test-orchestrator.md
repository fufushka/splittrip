# 0024. `npm test` — скрипт-оркестратор рівнів тестів на одній базі прогону

## Контекст і проблема

Одна команда має підняти все потрібне (Docker, Supabase, база `run_<id>`, міграції,
застосунок) і прогнати unit, інтеграційні й E2E (spec лаби 3, крит. 1, 6–12), а базу й
застосунок прибрати навіть після падіння етапу (крит. 8). `make` не використовуємо —
`npm run` (ADR-0014; `ai/lab3/007`, п. 5).

## Чинники рішення

- Прибирання навіть після падіння (крит. 8) і ненульовий код без Docker (крит. 7).
- Окремий підсумок кожного рівня у виводі (крит. 1).
- Без нових інструментів поруч із наявним Supabase CLI (ADR-0020).
- E2E — чорна скринька: зібраний `dist/main.js` окремим процесом (spec, «Рівні тестів»).

## Розглянуті варіанти

- Скрипт `scripts/test-all.ts` з етапами й прибиранням у `finally`
- Ланцюжок `&&` у `package.json`
- Docker Compose / testcontainers

## Рішення

Обрано **`scripts/test-all.ts`**: Docker → Supabase (`db:start`, якщо не запущено) →
`run_<id>` і міграції (спільний `scripts/run-db.ts`, на який переходить і `test-db.ts`) →
unit → інтеграційні з покриттям → збірка й старт застосунку → E2E → пороги покриття;
у `finally` — зупинка застосунку й видалення бази. Інтеграційні й E2E працюють на **одній**
`run_<id>`: користувачі Supabase Auth однаково спільні для всіх баз, а E2E реєструє власних.
Застосунок для E2E стартує оркестратор, а не тест-файл. Supabase після прогону не
зупиняється (`ai/lab3/007`, п. 5).

### Наслідки

- Добре: одна команда, прибирання гарантоване, підсумок кожного рівня.
- Добре: логіку бази прогону не дубльовано між `test:api:db` і `npm test`.
- Погано: ще один скрипт керування процесами (spawn, сигнали, таймаути) — сам потребує
  ручної перевірки (звіт `npm test -- --report`).
- Погано: `npm test` вимагає Docker, тож у hook-и не входить — лише вручну (C14).

### Підтвердження

C14: `npm test -- --report` пише `reports/npm-test.txt` з командою, HEAD і кодом виходу;
без запущеного Docker `npm test` завершується з кодом ≠ 0 до тестів; після прогону
`run_<id>` у локальному Supabase немає.

## Плюси й мінуси варіантів

### `scripts/test-all.ts`

- Добре: `finally` для прибирання; етапи й підсумки під контролем; той самий стиль, що
  `test-db.ts` і `demo-guards.ts`.
- Погано: власний код оркестрації.

### Ланцюжок `&&`

- Добре: нуль коду.
- Погано: після падіння нічого не прибирає — крит. 8 не виконується.

### Docker Compose / testcontainers

- Добре: стандартний спосіб підняти залежності тестів.
- Погано: новий інструмент, що дублює Supabase CLI (ADR-0020); Supabase Auth однаково
  потрібен із CLI.
