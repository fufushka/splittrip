# 0019. Ідемпотентність `POST`: заголовок `Idempotency-Key` і таблиця ключів

## Контекст і проблема

Клієнт, що не отримав відповіді (таймаут, обрив), повторює запит. Для `PUT` і `DELETE` повтор
безпечний за природою, для `POST` — ні: повтор `POST /expenses` створить другу витрату й
зламає баланси. Автор прийняв `Idempotency-Key` (`ai/lab2/004`, п. 15).

## Чинники рішення

- Повтор з тим самим ключем не створює другого запису й повертає ту саму відповідь.
- Помилкове повторне використання ключа з іншим тілом не маскується.
- Ключі ізольовані між користувачами.

## Розглянуті варіанти

- `Idempotency-Key` + таблиця `idempotency_keys` (модель Stripe, IETF draft)
- Клієнтські id і `PUT /trips/:id/expenses/:eid` для створення
- Без ідемпотентності (лише ретраї на сервері)

## Рішення

Обрано **`Idempotency-Key`**. Модуль `idempotency` (порт + логіка) і реалізація сховища в
`storage` / memory:

1. Перед обробкою: `INSERT … (owner_id, key, request_hash, status = 'in_progress')`;
   конфлікт → якщо збережено відповідь і хеш збігається, повернути її; хеш інший → `422`;
   ще `in_progress` → `409`.
2. Після обробки: зберегти статус і тіло відповіді (успіх або 4xx). 5xx не зберігається —
   ключ звільняється для ретраю.
3. Ключі старші за 24 год ігноруються й видаляються.

`request_hash` — SHA-256 від методу, шляху й тіла.

### Наслідки

- Добре: безпечні повтори для всіх `POST /trips*`; поведінка з відомого індустрійного патерну.
- Погано: ключ і бізнес-зміна — у **різних** транзакціях. Якщо процес упаде між комітом зміни
  і збереженням відповіді, ключ лишиться `in_progress`; після 24 год повтор виконає операцію
  вдруге. Свідоме обмеження, фіксується в аудиті; повне рішення — запис ключа в транзакції
  агрегату.
- Погано: ще одна таблиця й запис на кожен `POST`.

### Підтвердження

Крит. 8: повторний `POST` із тим самим ключем → та сама відповідь і 1 рядок; інше тіло →
`422`; паралельний дубль → `409`.

## Плюси й мінуси варіантів

### `Idempotency-Key` + таблиця

- Добре: працює для будь-якого `POST`, включно з `close`; відповідь відтворюється дослівно.
- Погано: дві транзакції (див. наслідки).

### Клієнтські id + `PUT`

- Добре: ідемпотентність без додаткової таблиці.
- Погано: змінює контракт, прийнятий у spec; не покриває `POST /close`.

### Без ідемпотентності

- Добре: нічого не робити.
- Погано: дублікати витрат і переказів при ретраях клієнта — порушення вимоги лаби.
