# 0013. Поїздка з учасниками, витратами й переказами — один модуль `trips`

## Контекст і проблема

Сценарії працюють із поїздкою, учасниками, витратами й переказами. Треба вирішити, як
розбити їх на модулі так, щоб межі були обґрунтовані й без циклів (spec.md, крит. 9, 10).

## Чинники рішення

- Правила «закрита поїздка не змінюється», «не прибрати згаданого учасника», «закрити лише
  за нульових балансів» (spec-fix-02, spec-fix-03) читають усі чотири сутності разом.
- Граф залежностей без циклів.
- Обчислення, яке не залежить від зберігання, має тестуватися окремо.

## Розглянуті варіанти

- Один модуль `trips` (агрегат) + чисті `balances` і `money`
- Окремі модулі `trips`, `participants`, `expenses`, `transfers`, `balances`
- Шари замість модулів: `routes/`, `services/`, `models/`

## Рішення

Обрано «один модуль `trips` + `balances` + `money`», бо межа модуля збігається з межею
узгодженості: усі інваріанти I3–I5 (architecture.md) перевіряються в одному місці й
однією транзакцією. Обчислення винесено в `balances`, яке не знає про `trips`.

### Наслідки

- Добре: граф без циклів — `trips → balances → money`.
- Добре: кожне правило домену — в одному модулі.
- Погано: `trips` найбільший модуль. Усередині він поділяється на файли за сутностями,
  але ззовні доступний лише `index.ts`.

### Підтвердження

`make boundaries`: немає модулів поза architecture.md, немає циклів, `balances` і `money`
не імпортують `trips`.

## Плюси й мінуси варіантів

### Один агрегат `trips`

- Добре: інваріанти в одному місці; без циклів.
- Погано: великий модуль.

### Модуль на кожну сутність

- Добре: дрібні модулі.
- Погано: цикл `trips → balances → expenses → trips` (закриття потребує балансів, витрати
  — статусу поїздки) або розмазані по модулях перевірки інваріантів.

### Шари

- Добре: звично для Express-проєктів.
- Погано: межі — за технікою, а не за доменом; spec вимагає зворотного.
