# 0018. Зміна агрегату: `update(tripId, mutate)` в одній транзакції з `FOR UPDATE`

## Контекст і проблема

Автор обрав «одна транзакція на весь агрегат» і `SELECT … FOR UPDATE` для паралельних
запитів (`ai/lab2/004`). Окремі `findById()` і `save()` не можуть утримати блокування між
викликами, а відкривати транзакцію в сервісі заборонено умовою лаби. Автор прийняв варіант
`update(tripId, mutate)` (`ai/lab2/005`, п. 1).

## Чинники рішення

- Транзакції й SQL — лише в `storage`; сервіси — лише бізнес-правила.
- Інваріанти I3–I5 і «закрити лише за нульових балансів» перевіряються на тому самому стані,
  який буде збережено (немає гонки «перевірив → хтось змінив → зберіг»).
- Ретрай тимчасових помилок без повторення побічних ефектів.

## Розглянуті варіанти

- `update(tripId, mutate)`: транзакція й блокування в `storage`, чиста `mutate` із сервісу
- `repo.transaction(fn)` — сервіс відкриває межу транзакції
- Оптимістичне блокування (`version`) без `FOR UPDATE`

## Рішення

Обрано **`update(tripId, mutate)`**. Всередині `storage`:
`BEGIN` → `SELECT … FROM trips WHERE id = $1 FOR UPDATE` → решта агрегату (3 запити) →
`mutate(trip)` (чиста доменна функція сервісу: спершу перевірка власника, далі новий `Trip`
або доменна помилка) →
порівняння зі станом до зміни за id → пакетні `INSERT` / `UPDATE` / `DELETE` → `COMMIT`.
На `40001`, `40P01` і обриві з'єднання транзакція повторюється до 3 разів з backoff; `mutate`
виконується знову на свіжому стані. `lock_timeout` 3 с, `statement_timeout` 5 с → `503`.

### Наслідки

- Добре: сервіс не бачить транзакцій; паралельні запити до однієї поїздки серіалізуються.
- Добре: доменна помилка в `mutate` → `ROLLBACK`, нічого не збережено.
- Погано: `mutate` зобов'язана бути чистою (без логів «успіху», мережі, часу поза аргументами);
  порушення помітне лише на рев'ю — `now` передається в `mutate` аргументом.
- Погано: diff агрегату в `storage` — найскладніший код лаби; покривається тестами на
  memory і postgres тим самим набором.
- Погано: блокування на рівні поїздки — паралельні зміни різних витрат однієї поїздки теж
  чекають одна одну (для сценаріїв SplitTrip прийнятно).

### Підтвердження

Крит. 7: паралельні `close` і `POST expenses` дають узгоджений стан. Крит. 8: підкинута
`40001` → успіх після ретраю; 3 поспіль → `503`.

## Плюси й мінуси варіантів

### `update(tripId, mutate)`

- Добре: межа транзакції = межа агрегату; сервіс без SQL.
- Погано: дисципліна чистоти `mutate`.

### `repo.transaction(fn)`

- Добре: гнучко, кілька операцій в одній транзакції.
- Погано: межею транзакції керує сервіс — порушення умови лаби; легко зробити мережевий
  виклик усередині транзакції.

### Оптимістичне блокування

- Добре: без очікування блокувань.
- Погано: клієнт отримує `409` на звичайні паралельні дії; автор обрав `FOR UPDATE`.
