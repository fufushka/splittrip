# 0017. Автентифікація: Supabase Auth через HTTP API, перевірка JWT за JWKS (`jose`)

## Контекст і проблема

Ініціатор — користувач Supabase Auth (`ai/lab2/004`); реєстрація, логін, refresh і logout —
у нашому API (`ai/lab2/006`); поїздку бачить лише власник (`ai/lab2/005`). Треба обрати, як
викликати Supabase Auth і як перевіряти токен на кожному запиті `/trips*`.

## Чинники рішення

- Кожен запит `/trips*` перевіряється локально, без мережевого виклику до Auth.
- Статичний етап (`STORAGE=memory`) працює без Supabase (spec, крит. 1).
- Паролі й токени не потрапляють у логи (крит. 6).
- Мінімум залежностей; `auth` — адаптер, домен про нього не знає.

## Розглянуті варіанти

- HTTP API Supabase Auth через `fetch` + `jose` (JWKS)
- `@supabase/supabase-js` (`auth.signUp`, `auth.getUser`)
- Перевірка JWT спільним секретом (HS256, `SUPABASE_JWT_SECRET`)

## Рішення

Обрано **`fetch` + `jose`**:

- `signup` / `login` / `refresh` / `logout` — виклики `/auth/v1/signup`,
  `/auth/v1/token?grant_type=password|refresh_token`, `/auth/v1/logout` з ключем проєкту.
- Перевірка доступу: `jose.jwtVerify` з `createRemoteJWKSet(<url>/auth/v1/.well-known/jwks.json)`
  (ключі кешуються), перевірка `iss`, `aud = authenticated`, `exp`. Ініціатор = `sub`.
- Для `STORAGE=memory` модуль `auth` має фейк: власна пара ключів, той самий `jwtVerify`.
- Помилки Supabase Auth відображаються в коди контракту: невідомий email і хибний пароль →
  однаковий `401`; зайнятий email → `409`; Auth недоступний → `503`.

### Наслідки

- Добре: перевірка токена — без мережі на кожен запит; ротація ключів Supabase — автоматично.
- Добре: одна маленька залежність (`jose`); `fetch` вбудований у Node 24.
- Погано: access-токен діє до `exp` навіть після `logout` (відкликається лише refresh-токен) —
  властивість stateless JWT; фіксується в аудиті як свідоме обмеження.
- Погано: формати відповідей Supabase Auth описуємо типами вручну.

### Підтвердження

Крит. 6: тести signup → login → запит, `401` на відсутній / підроблений / прострочений токен,
refresh після logout не діє, у логах немає `password` і токенів. C6: `jose` лише в `auth`.

## Плюси й мінуси варіантів

### `fetch` + `jose`

- Добре: локальна перевірка, без зайвого клієнта; легко підмінити фейком.
- Погано: ручні типи відповідей Auth.

### supabase-js

- Добре: офіційний клієнт, готові типи.
- Погано: `getUser()` — мережевий виклик на кожен запит; великий клієнт заради 4 викликів;
  тягне PostgREST-клієнт, яким ми не користуємось (ADR-0015).

### HS256 зі спільним секретом

- Добре: найпростіша перевірка.
- Погано: секрет підпису на сервері застосунку; Supabase переводить проєкти на асиметричні
  ключі, legacy-секрет застаріває.
