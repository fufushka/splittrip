# 0023. Покриття — вбудоване в Node, пороги на файл власним скриптом за lcov

## Контекст і проблема

Spec лаби 3 вимагає порогів покриття гілок на кожен файл критичної логіки: ≥ 90% на
`money`, `trips/domain`, `trips/service`, `idempotency` і 100% на `balances` (крит. 3), у
`npm run check`/pre-push і в `npm test` (крит. 4). Вбудовані пороги Node
(`--test-coverage-branches` тощо) рахують лише сумарний відсоток усіх файлів. У `balances`
одна гілка недосяжна (`?? ZERO`, рядок 55): ключі `totals` — рівно `participantIds`.

## Чинники рішення

- Без нової залежності для покриття (`ai/lab3/007`, п. 3).
- Поріг саме на файл, а не сумарний.
- Перевірка має вміти впасти (C10) і розрізняти «нижче порогу» й «не вдалося перевірити».

## Розглянуті варіанти

- Вбудоване покриття + lcov-репортер + `scripts/check-coverage.ts` на файл
- Лише вбудовані `--test-coverage-*`
- c8 `--per-file --check-coverage`

## Рішення

Обрано **вбудоване покриття з lcov і власним скриптом**: `npm run test:cov` — один запуск
`node --test` над `test/unit` і `test/api` з lcov у `coverage/lcov.info`;
`scripts/check-coverage.ts` читає `BRF`/`BRH` кожного файлу й порівнює з таблицею порогів.
Покриття «unit + інтеграційні» в `npm test` — теж один спільний запуск, бо Node зводить
покриття лише в межах одного запуску (`ai/lab3/012`, п. 2). Недосяжна гілка `balances` —
коментар `/* node:coverage ignore next */` із причиною (`ai/lab3/012`, п. 1; spec-fix-01):
Node зараховує її покритою в `BRF`/`BRH`, хоча сирий `BRDA` лишається 0.

### Наслідки

- Добре: жодної нової залежності; той самий інструмент у check і в `npm test`.
- Добре: недосяжна гілка задокументована в коді, а не прихована зниженим порогом.
- Погано: власний скрипт (~50 рядків), який треба підтримувати й перевіряти сценарієм demo.
- Погано: «гілка» — у метриці V8 (блоки, правий операнд `??`/`||`), а не istanbul; числа
  не порівнюються напряму з іншими інструментами.
- Погано: unit-тести в `npm test` виконуються двічі (≈ 0,3 с).

### Підтвердження

C13: `npm run coverage` у check і pre-push; сценарій `npm run demo` 09 — прибраний тест
`balances` → `check-coverage` падає з рядком `balances … НИЖЧЕ`.

## Плюси й мінуси варіантів

### Вбудоване + lcov + скрипт

- Добре: без залежностей; поріг на файл; код виходу під нашим контролем.
- Погано: свій код; lcov нумерує гілки індексом, тож lcov різних запусків не зводяться.

### Лише вбудовані `--test-coverage-*`

- Добре: нуль коду.
- Погано: лише сумарний поріг; поріг на файл — п'ять окремих запусків.

### c8

- Добре: `--per-file`, HTML-звіт, зводить кілька процесів.
- Погано: +1 залежність — автор відхилив (`ai/lab3/007`, п. 3).

## Додаткова інформація

Промпти: `ai/lab3/007` (п. 3), `010` (п. 1), `012` (п. 1, 2, 4). Spec лаби 3, крит. 2–5;
spec-fix-01. Пов'язані: ADR-0004, ADR-0024.
