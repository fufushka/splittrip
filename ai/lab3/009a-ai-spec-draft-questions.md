## 1. Поріг у check

Який поріг покриття стоїть у npm run check і pre-push (без Docker) і для якого порогу робити
сценарій падіння в npm run demo? Зараз на unit + API-тестах на memory критичні файли мають
уже ≥ 90% гілок (найнижче — balances, 91,3%).

- **Усі пороги в check (Recommended)** — check міряє unit + API на memory: гілки ≥ 90% на 5
  критичних файлах і 100% на balances. Тобто кожен push тримає поріг критичної логіки. npm
  test перевіряє те саме на unit + інтеграційних. Сценарій у demo — без Docker.
- **Лише balances 100% у check** — check запускає unit-тести з порогом 100% на balances;
  поріг ≥ 90% для решти — лише в npm test. Сценарій у demo — для balances. Так агент
  прочитав 007 п. 9.
- **Пороги лише в npm test** — check порогів не має; сценарій у demo — для npm test, тож
  demo потребуватиме Docker.

## 2. Фікс багів

Як саме виправляти баг лаб 1–2, якщо нові тести його знайдуть (ви вирішили — в гілці лаби
3)? CLAUDE.md забороняє ручний патч без зміни входу (spec / критерій).

- **Червоний тест → фікс (Recommended)** — Спершу коміт тесту, що відтворює баг, потім коміт
  фіксу з посиланням на порушений критерій лаби 1–2. Якщо такого критерію немає — спершу
  spec-fix лаби 3 із вашим прийняттям. У історії видно, що тест зловив баг.
- **Тест і фікс одним комітом** — Простіше, але в історії не видно, що тест спершу падав.
  Посилання на критерій — у тілі коміту.

## 3. Auth-тест

test/unit/supabase-auth.test.ts піднімає локальний HTTP-сервер-фейк Supabase (listen на
127.0.0.1), тобто має I/O, а ви визначили unit як «без I/O». Як його класифікувати?

- **Уточнити unit (Recommended)** — Unit = без справжніх зовнішніх залежностей (БД,
  Supabase); фейк у процесі тесту дозволений. Тест лишається в unit і в швидкому check.
- **Перенести до інтеграційних** — Визначення unit «без I/O» лишаємо; тест їде в етап
  «інтеграційні» npm test, хоча справжнього Supabase він не потребує.

## 4. Тести storage

У питанні про рівні я написав про «тести адаптерів storage/postgres», ніби вони вже є. Це
неточно: окремих таких тестів немає. Є test/api/postgres.test.ts (поведінка на БД, зокрема
блок «сховище напряму») і всі API-тести на Postgres. Чи потрібні нові прямі тести адаптера?

- **Наявних достатньо (Recommended)** — Інтеграційні = test:api:db + postgres.test.ts; у spec
  назвати файли, а не «тести адаптерів». Звіт покриття npm test покаже, що з
  storage/postgres не покрито.
- **Додати прямі тести адаптера** — Новий файл: TripRepository на Postgres напряму — create /
  findById / list / update з блокуванням / delete. Сильніше показує «взаємодію компонентів»,
  але це більше роботи.

Чи стає npm run mutation рядком у checks.md 0.5? Зараз у крит. 21 чернетки — лише npm test

## 6. Звіт «до»

Звіт Stryker «до» знімається ще до нових тестів, тож з порогом break 100% на balances npm
run mutation на ньому впаде (код ≠ 0). Як діяти?

- **Звіт з падінням (Recommended)** — Поріг налаштовано з початку; звіт «до» записує
  ненульовий код і вижилих мутантів — це доказ прогалини. Звіт «після» — код 0.
- **Поріг — після підсилення** — Звіт «до» — без порога; break 100% вмикає окремий коміт
  після нових тестів.
