## 2. Покриття npm test (В2)

Вбудоване покриття Node зводить дані лише в межах одного запуску node --test. Тож покриття
«unit + інтеграційні» у npm test можна виміряти лише спільним запуском. Як робити?

- **Один запуск (Recommended)** — Етап інтеграційних — один запуск test/unit + test/api на
  Postgres із покриттям; unit-тести виконуються вдруге (≈ 0,3 с). Підсумок кожного рівня дає
  власний репортер за теками.
- **Окремий прогін покриття** — Ще один прогін інтеграційних у другій базі run_<id> (+20–30
  с, дві бази): postgres.test.ts не можна вдруге прогнати на тій самій базі.

Крит. 2: «unit-тести самі дають balances 100% рядків і гілок — звіт покриття npm run

## 5. TS-checker (В5)

Додавати @stryker-mutator/typescript-checker? Наш TS перед запуском не компілюється (Node
просто стирає типи), тож без checker мутанти з помилками типів виконуються й можуть
«вижити». Вирішити треба до звіту «до».

- **З checker (Recommended)** — Мутанти, які tsc відхилив би, автоматично отримують
  CompileError і не рахуються вижилими — менше ручної класифікації. Ціна: +1 залежність і
  повільніший запуск. Сумісність із нашим tsconfig перевірить перший сеанс реалізації.
- **Без checker** — Менше залежностей і швидше. Вижилі мутанти з помилками типів
  класифікуємо вручну: «прийнятний — tsc відхилив би».
