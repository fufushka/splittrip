## 1. Рівні тестів

Як розділити рівні тестів лаби 3? Зараз є: unit (test/unit); API-тести через app.inject на
memory (C11) і на Postgres + Supabase Auth (C12); smoke без БД. E2E немає.

- **inject + справжні БД/Auth (Recommended)** — Інтеграційні = застосунок у процесі тесту
  (app.inject) зі справжніми Postgres run_<id> і Supabase Auth (наявний test:api:db) + тести
  адаптерів storage/postgres. E2E = зібраний dist/main.js окремим процесом на порту, fetch по
  мережі. API на memory лишаються швидким шаром у check, але інтеграційними не вважаються.
- **Інтеграційні через сокет** — Те саме, але інтеграційні теж піднімають справжній
  HTTP-сервер (listen на порту 0 + fetch), бо в умові «з підняттям … HTTP-сервер».
  Повільніше, і треба змінити harness.

## 2. Unit-модуль

Який один невеликий модуль покрити unit-тестами повністю (100% рядків і гілок; кожен мутант
вбитий або обґрунтовано еквівалентний)?

- **balances (Recommended)** — computeBalances + suggestTransfers, 87 рядків; зараз 100%
  рядків і 91% гілок. Жадібний розрахунок із правилом «за рівних сум — раніший у списку» дає
  реальні випадки.
- **money** — allocateEqually й арифметика, 44 рядки; уже 100/100 — показати мало.
- **trips/domain** — Інваріанти поїздки, 180 рядків; зараз 100/92,5. Найбільше роботи.

## 3. Покриття

Як міряти й обмежувати покриття гілок критичної логіки (money, balances, trips/domain,
trips/service, idempotency) на прогоні unit + інтеграційних?

- **Node, ≥90% / 100% (Recommended)** — Вбудоване покриття Node
  (--experimental-test-coverage), без нової залежності. Гілки ≥ 90% на кожному критичному
  файлі, 100% на unit-модулі. Нова перевірка в checks.md + сценарій її падіння в demo (C10).
- **c8, ті самі пороги** — c8 дає HTML-звіт, але це +1 залежність (пояснення «навіщо» в
  README + ADR).
- **Node, лише звіт** — Покриття міряємо й кладемо у reports/, порогів не ставимо.

## 4. Мутації

Який обсяг мутаційного тестування Stryker (зі списку умови для TypeScript підходить лише
він)? Мутанти ганяються проти unit- і API-тестів на memory, без Docker.

- **Доменна логіка (Recommended)** — money, balances, trips/domain, trips/service. Вижилі —
  у звіт із класом «реальна прогалина / еквівалентний / прийнятний». Поріг break — лише на
  unit-модулі, 100%; еквівалентні мутанти — з коментарем Stryker disable і причиною.
- **Увесь src** — Найповніше, але сотні мутантів і довгий ручний розбір вижилих; мутантів
  postgres-адаптерів без БД однаково не вбити.
- **Лише unit-модуль** — Найменше роботи, але не видно, наскільки ефективні тести решти
  логіки.

## 5. Одна команда

Яка одна команда піднімає все (Docker/Supabase, база run_<id>, міграції, сервіс) і запускає
unit → інтеграційні → E2E з покриттям? Мутації — окремою командою npm run mutation.

- **npm test, Supabase лишається (Recommended)** — Стандартна назва npm (ADR-0014: npm run
  замість make). Після прогону базу run_<id> видаляє, сервіс зупиняє, а Supabase лишає
  запущеним: повторний старт — ~1 хв.
- **npm test, усе зупиняє** — Наприкінці ще supabase stop: після прогону чистий стан, але
  кожен запуск +~1 хв.

## 6. E2E (кілька варіантів)

Які E2E-сценарії входять у лабу 3? E2E — зібраний сервіс на порту, справжні БД і Auth,
запити fetch. Можна кілька.

- **Повний шлях (Recommended)** — signup → login → POST /trips → учасники → витрати →
  balances → settlements → перекази за пропозицією → нульові баланси → close 200.
- **Доступ (Recommended)** — Другий користувач отримує 404 на чужу поїздку; після logout
  refresh-токен не діє.
- **Ідемпотентність по мережі** — Повтор POST з тим самим Idempotency-Key → той самий
  результат і 1 рядок у БД.
- **/version = git sha** — GET /version повертає sha поточного коміту — це те, що DEFENSE
  §4 просить зафіксувати.

## 7. Аудит тестів

Звідки брати топ-3 випадки, де «зелені» тести не ловлять реальні баги? Кожен випадок →
тест-підсилення окремим комітом.

- **Вижилі мутанти (Recommended)** — Мутанти класу «реальна прогалина». Для кожного:
  файл:рядок і що змінено, тест, що його вбиває, коміт test: … і звіт до/після.
- **Внесені баги** — Bug seeding на рівні інтеграційних тестів чи E2E: свідомо ламаємо код,
  показуємо, що тести мовчать, і підсилюємо їх.
- **Змішано** — 2 випадки з вижилих мутантів + 1 внесений баг на рівні інтеграційних тестів.

ефективності тестів і топ-3 слабких тестів. Як вмістити це в одну сторінку?

- **Новий §5 у DEFENSE (Recommended)** — §2 — топ-3 розбіжностей AI, як завжди. §5
  «Ефективність тестів» — mutation score до → після, топ-3 слабких тестів → коміти, npm run
  mutation, посилання на повний звіт.
- **Окремий звіт** — Слабкі тести й аналіз — у reports/test-audit.md, а в DEFENSE — 1–2
  рядки й посилання.

## 9. Конвеєр

Як тримати узгодженим ланцюг «код ↔ тести ↔ конвеєр»? CI немає (у лабі 2 — «Не входить»).
Конвеєр — hook-и: pre-commit і pre-push запускають npm run check.

- **Hook-и, без CI (Recommended)** — Нові unit-тести й поріг покриття unit-рівня — у npm run
  check і pre-push. Повний npm test з Docker — вручну перед здачею, як C12.
- **GitHub Actions: check** — Workflow на push і PR з npm run check, без Docker-БД.
- **GitHub Actions: повний test** — Workflow з повним npm test: Supabase у CI через Docker.
  Найсильніший доказ, але й найбільше роботи.
