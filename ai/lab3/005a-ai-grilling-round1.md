1. **Ваш абзац наміру.** За DoD §4 AI оформлює spec лише з вашого входу: вашого власного абзацу наміру + відповідей. «Ось вимоги, зроби спеку» не приймається. 2. **Рівні тестів — терміни.** Пропоную такі визначення:
   - *unit* — чистий модуль без I/O;
   - *інтеграційні* — застосунок у процесі тесту (`app.inject`) зі справжніми залежностями: Postgres (база `run_<id>`) і Supabase Auth. Тобто наявний `test:api:db` + тести адаптерів `storage/postgres`;
   - *E2E* — зібраний `dist/main.js` окремим процесом на вільному порту, справжні БД і Auth, запити `fetch` по мережі, сценарій користувача;
   - API-тести на `memory` (C11) лишаються швидким шаром у `npm run check`, але до інтеграційних не зараховуються.

   Альтернатива — інтеграційні теж через справжній сокет (`listen` на порту 0 + `fetch`), бо в умові сказано «з підняттям … HTTP-сервер». Рекомендую перший варіант: сокет перевіряє E2E, а `inject` швидший і вже є.

3. **Модуль для повного unit-покриття.** Рекомендую `balances` (`computeBalances`, `suggestTransfers`, 87 рядків): у жадібному розрахунку з правилом «за рівних сум — раніший у списку» є що перевіряти. «Повністю» означає 100% рядків і гілок, і кожен мутант модуля або вбитий, або обґрунтовано еквівалентний. Альтернативи:
   - `money` — уже 100%, показати майже нічого;
   - `trips/domain` — 180 рядків, більше роботи;
   - `idempotency`.

5. **Мутаційне тестування.** Зі списку для TypeScript підходить лише Stryker.
   - **Обсяг:** `money`, `balances`, `trips/domain`, `trips/service` проти unit- і API-тестів на `memory`. Без Docker: прогін на БД для кожного мутанта — надто повільно.
   - **Звіт:** вижилі мутанти — у `reports/` з класом «реальна прогалина / еквівалентний / прийнятний» і причиною.
   - **Поріг падіння (`break`):** не ставимо, крім модуля з п. 3 — там 100%. Еквівалентні мутанти позначаємо коментарем `Stryker disable` з причиною.

   Альтернативи: увесь `src` або лише модуль із п. 3.

6. **Одна команда.** `npm test` — стандартна назва в npm; `make` не потрібен, бо ADR-0014 і DoD §5 дозволяють `npm run`. Що вона робить по черзі:
   1. перевіряє Docker;
   2. запускає `supabase start`, якщо він ще не запущений;
   3. створює базу `run_<id>` і накочує міграції;
   4. проганяє unit-, потім інтеграційні тести;
   5. збирає й стартує сервіс, проганяє E2E;
   6. рахує покриття з порогами з п. 4;
   7. видаляє базу й зупиняє сервіс.

   Supabase після прогону лишається запущеним: повторний старт займає ~1 хв. Мутації — окремою командою `npm run mutation`: вони довгі, і в умові їх названо окремо.

7. **E2E-сценарії.** Пропоную два:
   - **повний шлях:** `signup` → `login` → `POST /trips` → учасники → витрати → `GET balances` → `GET settlements` → перекази за пропозицією → нульові баланси → `close` 200;
   - **доступ:** другий користувач отримує 404 на чужу поїздку; після `logout` refresh-токен не діє.

   Можна додати: ідемпотентний повтор `POST` по мережі; `/version` віддає sha коміту, який вимагає DEFENSE §4 (`resolveVersion` уже читає `git rev-parse HEAD`).

8. **Аудит «зелені тести не ловлять баги».** Пропоную брати топ-3 з вижилих мутантів класу «реальна прогалина». Для кожного: мутант (файл:рядок, що змінено), тест, що його вбиває, коміт `test: …` і звіт до/після. Альтернатива — свідомо внесені баги (bug seeding) на рівні інтеграційних тестів чи E2E.

9. **DEFENSE: два топ-3.** DoD §4 вимагає топ-3 розбіжностей «spec ↔ вихід AI», а лаба 3 — ще топ-3 слабких тестів і аналіз ефективності тестів. Щоб усе влізло на одну сторінку, пропоную:
   - §2 — топ-3 розбіжностей AI, як завжди;
   - новий §5 «Ефективність тестів» — mutation score до → після, топ-3 слабких тестів → коміти, посилання на повний звіт і `npm run mutation`.

   Альтернатива: слабкі тести — лише в `reports/test-audit.md`, а в DEFENSE — посилання на нього.

10. **Конвеєр.** Умова вимагає тримати узгодженим ланцюг «код ↔ тести ↔ конвеєр». Наш конвеєр — hook-и: pre-commit і pre-push запускають `npm run check`. Рекомендую:
    - CI не робимо, як і в лабі 2;
    - нові unit-тести й поріг покриття unit-рівня — у `npm run check` і pre-push;
    - повний `npm test` з Docker — вручну перед здачею, як C12.

    Альтернативи: GitHub Actions з `npm run check` або GitHub Actions з повним `npm test` (Supabase у CI).
