## 1. Баги лаб 1–2

Якщо нові тести лаби 3 знайдуть справжній баг у коді лаб 1–2, де його виправляти? DoD §5
і commits.md: виправлення попередньої роботи — окрема гілка й PR, не в PR наступної. PR #2
(лаба 2) ще відкритий.

- **Гілка fix/lab2-… (Recommended)** — Виправлення + тест — у fix/lab2-<slug> від
  feature/lab2-api-db, з окремим PR. Гілку лаби 3 оновлюємо merge-комітом з fix-гілки.
  Аудит лаби 3 посилається на цей PR.
- **У гілці лаби 3** — Простіше: баг — результат тестування. Відхилення від DoD §5;
  причину фіксуємо в spec.
- **Не виправляти в лабі 3** — Тест позначаємо todo з причиною, баг — у звіт і DEFENSE як
  відомий. Виправлення — пізніше.

## 3. E2E ідемпотентність

E2E «ідемпотентність по мережі»: як перевіряти, що після повтору POST з тим самим
Idempotency-Key створено рівно 1 запис?

- **Через API (Recommended)** — Чорна скринька: обидва POST повертають той самий id, а
  GET /trips/:id показує одну витрату. E2E не залежить від схеми БД.
- **SQL-запитом до БД** — Сіра скринька: тест рахує рядки в базі run_<id>. Сильніший доказ
  «1 рядок», але E2E знатиме схему.

## 4. Звіти

Які звіти мутацій комітити в reports/? За checks.md звіт — це справжній вивід команди з
першим рядком-командою. HTML-звіт Stryker — один файл на кілька МБ.

- **Текст + класифікація (Recommended)** — Комітимо текстовий вивід Stryker «до» і «після»
  (.txt) та mutation-analysis.md із класом кожного вижилого мутанта. HTML генерує npm run
  mutation локально, він у .gitignore.
- **Ще й HTML** — Те саме + HTML-звіт у репо: рев'юеру зручно дивитися, але це великий
  згенерований файл.
