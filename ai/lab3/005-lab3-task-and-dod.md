Мета: unit + інтеграційні + E2E + мутаційне тестування.

Що зробити:
• Передумова: розумне покриття критичної логіки (гілки, не лише рядки).
• Unit-тести: достатньо одного невеликого модуля, покритого повністю (усі його випадки) — мета показати вміння, а не покрити всю програму. Інтеграційні (з підняттям залежностей: БД, HTTP-сервер), E2E.
• Одна команда (напр. make test) піднімає все потрібне (БД/Docker, міграції, сервіс) і запускає всі тести.
• Мутаційне тестування (Stryker / PIT / mutmut / cosmic-ray). Звіт: класифікувати вижилих мутантів (реальна прогалина / еквівалентний / прийнятний).
• Аудит: топ-3, де «зелені» тести не ловлять реальні баги; підсилити.
• DEFENSE.md: аналіз ефективності тестів + make mutation для відтворення.

Ознаки відмінного виконання: є всі рівні тестів; звіт мутацій із класифікацією вижилих; видно підсилення слабких тестів; прогін відтворюваний однією командою.

ОБОВ'ЯЗКОВІ АРТЕФАКТИ (кожне завдання):
- spec.md (≤1 стор.): що і навіщо, критерії прийняття (пишеться власноруч, і з AI; критерії фіксуються комітом, не лише в DEFENSE).
- Код через коміти + артефакти запуску (звіт + make … для відтворення).
- Аудит: топ-3, де реалізація розійшлася зі spec / «зрізані кути» + виправлення через зміну spec/критеріїв/стандарту (не ручний патч).
- DEFENSE.md (1 стор.): точка входу для рев'ю.
- ADR на ключові рішення (за MADR).

ШАБЛОН DEFENSE.md:
1. Що і навіщо (1-2 речення).
2. Топ-3 розбіжності / зрізані кути (проти spec) -> коміт.
3. Ключове рішення - альтернативи й чому обрав (adr/…).
4. Перевірка: make <ціль> -> результат; версія /version: <sha>.

НАСКРІЗНА ВИМОГА: працювати з артефактами живої системи (тести, CI, профайлер, БД) і тримати узгодженим ланцюг код <-> тести <-> конвеєр. Найсильніший доказ — звіт разом зі способом його відтворити.

ДВА ШЛЯХИ:
- Без AI: слід - це ваша історія рішень і самоперевірка проти spec.
- З AI: додатково повний слід промптів (ai/) і аудит виходу AI (топ-3 його «зрізаних кутів»); для кожної розбіжності - посилання на промпт, фідбек-коментар і додаткову spec.

Обидва шляхи мають однакову планку якості та бюджет рев'ю. Оцінюється розуміння й захист рішень, а не інструмент.

ЧЕКЛИСТ «ГОТОВО»: DEFENSE (1 стор.) · spec (≤1 стор.) з критеріями · топ-3 розбіжності з комітами · код + артефакти запуску (make …) · ADR · реалістична git-історія · чистий репозиторій.
