Перед тим як писати spec, лишилось 4 питання. Перше блокує роботу: ваші рішення в нинішньому вигляді не можна поєднати.

**1. `save(trip)` + `SELECT … FOR UPDATE` не працюють як два окремі виклики.**
Блокування живе лише до кінця транзакції. Якщо сервіс викликає `findById()`, а потім `save()`, між ними блокування вже немає. Протримати його можна, лише якщо транзакцію відкриє сервіс, а умова лаби це забороняє.

- **(a) Рекомендую.** Порт `repo.update(tripId, (trip) => newTrip)`. Шар `storage` відкриває транзакцію, робить `SELECT … FOR UPDATE` на рядок поїздки, завантажує агрегат, викликає вашу доменну функцію, зберігає зміни (diff за id) і робить коміт. Це досі «одна транзакція на весь агрегат», SQL і транзакція лишаються в `storage`. Під час ретраю функція виконується повторно, тому вона має бути чистою, і доменні функції в нас саме такі.
- **(b)** `repo.transaction(() => { findById; save })`. Межею транзакції фактично керує сервіс, це на межі порушення умови.

**2. Хто має доступ до поїздки?** Учасники не є обліковими записами (spec-fix-03 п. 4). Тому пропоную, щоб читати й змінювати поїздку міг лише її власник, тобто `sub` із JWT того, хто її створив. Що повертати чужому користувачеві?

- **`404` (рекомендую):** не видає, що такий id існує. Так робить GitHub.
- **`403`:** чесніше, але дозволяє перебирати id.

**3. Потік Supabase Auth.** Пропоную так:
- У нашому API немає реєстрації й логіну. Клієнт отримує JWT напряму від Supabase Auth.
- Ми перевіряємо підпис через JWKS (асиметричні ключі Supabase) бібліотекою `jose`. Без токена або з невалідним токеном повертаємо `401`.
- `owner_id` — це `sub` без зовнішнього ключа на `auth.users`. Причина: тести ганяємо в окремій базі на кожен прогін, а схема `auth` є лише в основній базі.
- Тестових користувачів створює admin API локального Supabase.

**4. Де саме Supavisor.**
- Локально Supabase CLI піднімає Postgres на `54322`. Для кожного прогону тестів створюємо окрему базу `run_<id>` і підключаємося до неї напряму, бо локальний пулер не працює з довільними базами.
