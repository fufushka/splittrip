## Що таке «протягування залежностей»

Це коли кожна функція отримує параметрами все, що потрібно функціям нижче за викликом, навіть якщо сама цим не користується:

```ts
// ❌ протягування: db, user, processId, logger йдуть крізь усі рівні
route(req) → addExpense(db, logger, user, processId, tripId, body)
  → checkTripOpen(db, logger, processId, tripId)
    → tripRepo.findById(db, logger, processId, tripId)
```

Додали нову наскрізну річ, наприклад транзакцію чи таймзону, і доводиться міняти сигнатури всіх функцій. Сервіс бачить `db`, хоча SQL йому знати не можна.

Лаба вимагає три речі без такого протягування:

1. **Ініціалізовані ресурси (пул БД).** Вони створюються один раз на старті й передаються в конструктор або фабрику репозиторію. Сервіс отримує вже готовий `tripRepo` і не знає, що за ним Postgres.
2. **Користувач-ініціатор і 3. business-process ID.** Ці дані різні для кожного запиту. Їх кладуть у «контекст запиту», наприклад `AsyncLocalStorage`: значення, видиме всюди в межах одного асинхронного ланцюжка викликів. Роут один раз робить `context.run({ user, processId }, …)`. Логер має `mixin`, який підтягує `processId` з контексту, і тоді будь-який `log.info()` з будь-якого рівня містить ID без жодного параметра.

```ts
// ✅ сервіс: лише бізнес-аргументи
async addExpense(tripId, input) {
  const { user } = requestContext();         // хто ініціатор
  log.info({ tripId }, 'add expense');       // processId потрапить сам
  ...
}
```

Варіанти, які називає умова, для ADR: ручний composition root + ALS, DI-контейнер (awilix, tsyringe) або Effect.

## Допит, раунд 1

Біля кожного питання є моя рекомендація. Можна відповісти «ок усе, крім N: …».

### Процес

2. **Makefile чи `npm run`** (з минулого аналізу)? Рекомендую новий ADR, що замінює ADR-0008, і перейти на `npm run`.
3. **PR #1 лаби 1:** мерджимо зараз, щоб гілка лаби 2 пішла від `main`? Рекомендую так.

### Архітектура (конфліктує з прийнятим у лабі 1)
4. **Де живе SQL.** Правило 4 в `architecture.md` забороняє доменному `trips` імпортувати зовнішні пакети, тож SQL у `trips` бути не може. Рекомендую розкласти так:
   - роути — `http`;
   - сервіси — сценарії в `trips`, залежать лише від порту `TripRepository`;
   - репозиторії — новий модуль-адаптер `storage` з SQL і транзакціями;
   - контекст запиту — модуль `context`.

   Граф в `architecture.md` змінюється, це spec-fix або новий розділ архітектури.
5. **Форма репозиторію.** Зараз порт виглядає як `findById(trip)` / `save(trip)`: зберігається весь агрегат. Є два варіанти:
   - **(a)** `save(trip)`: одна транзакція на весь агрегат. Просто, але потрібен diff «що змінилось».
   - **(b)** методи на кожну операцію (`addExpense`, `closeTrip`, …), кожен у своїй транзакції. Порт стає ширшим, зате SQL точний.

   Рекомендую (b): `findById` вантажить поїздку 4 запитами без N+1, а зміни йдуть точковими SQL-запитами.
6. **Паралельні запити.** Що буде, якщо одночасно закривають поїздку і додають у неї витрату? Варіанти:
   - `SELECT … FOR UPDATE` на рядок поїздки в кожній транзакції, що змінює дані;
   - колонка `version` (оптимістичне блокування) і `409` при конфлікті.

   Рекомендую `FOR UPDATE`: простіше, і клієнту не треба передавати версію.

### Користувач і доступи
7. **Хто такий «користувач-ініціатор»?** Автентифікація у нас поза обсягом (spec-fix-03 п. 8), але умова вимагає ініціатора, а сервіси мають знати про «доступи». Варіанти:
   - **(a)** заголовок `X-User-Id` (UUID) без автентифікації. Поїздка має `owner_id`, змінювати її може лише власник, інакше `403`.
   - **(b)** той самий заголовок лише для логів, без перевірок доступу.
   - **(c)** справжній Supabase Auth (JWT).

   Рекомендую (a): перевірка доступу стає реальним правилом сервісу, а автентифікацію чесно позначаємо як out of scope.
8. **Business-process ID:** беремо із заголовка `X-Request-Id`, якщо клієнт його передав, інакше генеруємо UUIDv7. Повертаємо в заголовку відповіді й у тілі помилки. Ок?

### API
9. **REST-ресурси, вкладені в поїздку:**
   - `POST /trips`, `GET /trips/:id`
   - `POST|DELETE /trips/:id/participants[/:pid]`
   - `POST|PUT|DELETE /trips/:id/expenses[/:eid]`
   - `POST|DELETE /trips/:id/transfers[/:tid]`
   - `GET /trips/:id/balances`, `GET /trips/:id/settlements`
   - `POST /trips/:id/close`

   Чи потрібен `GET /trips` (список поїздок власника)? Рекомендую так, з простою пагінацією `limit`/`cursor`. Ще рекомендую зміну витрати через `PUT` (повна заміна), бо частки однаково перераховуються.
10. **Формат помилок:** RFC 9457 `application/problem+json` з полями `type`, `title`, `status`, `detail`, `code`, `requestId`. Коди: `400` — форма запиту, `403` — доступ, `404`, `409` — стан (поїздка закрита, учасник згаданий, баланси ≠ 0), `422` — бізнес-валідація (Σ часток ≠ сума), `503` — БД недоступна. Ок?

### БД (Supabase)
11. **Як підключатись.** `supabase-js` ходить через REST (PostgREST) і **не підтримує транзакцій**, тож вимогу лаби з ним не виконати. Рекомендую пряме підключення до Postgres через Supavisor pooler і бібліотеку **postgres.js**: SQL tagged templates, як радить умова, вбудований пул, `sql.begin()` для транзакцій, жодного ORM. Альтернативи для ADR: Kysely (query builder), Drizzle (ORM), `pg` + `sql-template-tag`.
12. **Ізольоване середовище** («окрема база на прогін», не 5432–5434 на localhost):
    - **(a)** окрема схема `run_<id>` на кожен прогін тестів у хмарному Supabase, з видаленням після прогону;
    - **(b)** локальний Supabase CLI в Docker (порт 54322);
    - **(c)** Supabase branching (платний).

    Чи є у вас Docker? Без Docker рекомендую (a).
13. **Міграції:** звичайні `.sql` файли в `db/migrations/` і маленький власний раннер із таблицею `schema_migrations`, чи Supabase CLI migrations? Рекомендую звичайні SQL і власний раннер: не прив'язуємось до CLI, і цей раннер же створює тестову схему для п. 12.
14. **ID:** UUIDv7 генерує застосунок, а не БД. ID відомий до INSERT, це допомагає ідемпотентності. Ок?

### Збої та ідемпотентність
15. **Ідемпотентність:** заголовок `Idempotency-Key` на всіх `POST`, як у Stripe. Таблиця `idempotency_keys` зберігає ключ, користувача, хеш тіла й збережену відповідь. Повтор із тим самим ключем повертає ту саму відповідь. Той самий ключ з іншим тілом дає `422`. `PUT` і `DELETE` ідемпотентні за природою. Ок?
16. **Ретраї й таймаути.** Пропоную:
    - повтор транзакції лише на тимчасових помилках (`40001` serialization, `40P01` deadlock, обрив з'єднання) — до 3 спроб з backoff, у шарі `storage`;
    - `statement_timeout` 5 с;
    - БД недоступна → `503` + `Retry-After`;
    - на старті `SELECT now()`, і якщо не вдалося — процес одразу падає;
    - `/health` лишається liveness, додаємо `/ready` з перевіркою БД.

    Ок, чи інші числа?
17. **Етап «статика»:** in-memory реалізація того самого порту `TripRepository` з seed-даними, вибір через `STORAGE=memory|postgres`. Один набір API-тестів ганяємо проти обох реалізацій: це доказ, що сценарії працюють спершу на статиці, потім на БД. Ок?
