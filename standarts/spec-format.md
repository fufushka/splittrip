# Стандарт: формат spec

Версія: 0.1 · Статус: прийнято

## Розташування

- `docs/specs/labN-<slug>/spec.md` — одна spec на лабу (задачу).
- `docs/specs/labN-<slug>/spec-fix-NN.md` — додаткова spec: уточнення або виправлення вже
  прийнятої spec. Нумерація в межах лаби: `01`, `02`, …

## Обсяг і мова

- Не більше 1 сторінки (орієнтир — до ~80 рядків по 90 символів).
- Українською; назви файлів, команд, ендпоінтів — як у коді.

## Обов'язкові розділи spec.md

1. **Що і навіщо** — 2–4 речення: що робимо і яку проблему це розв'язує.
2. **Обсяг** — «Входить» / «Не входить».
3. **Критерії прийняття** — нумерований список. Кожен критерій:
   - перевіряється командою, файлом або історією git (указано, чим саме);
   - атомарний: один критерій — одна перевірювана властивість;
   - без слів «зручно», «швидко», «якісно» без числа чи правила.
4. **Обмеження** — що не можна робити чи змінювати, правила процесу.

Додаткові розділи дозволено, якщо вони є вхідними даними для критеріїв (напр. «Функціонал
продукту»).

## Обов'язкові розділи spec-fix-NN.md

1. **Що і навіщо** — яку spec доповнює, яку розбіжність закриває, посилання на промпт,
   фідбек або пункт аудиту, що її виявили.
2. **Уточнення** — нумеровані, кожне з посиланням на критерій, який уточнює (`до крит. N`).
3. **Критерії прийняття** — як перевірити, що уточнення виконано.
4. **Обмеження** — або «ті самі, що в spec.md».

Пріоритет: за розбіжності spec-fix з більшим номером переважає.

## Життєвий цикл

Чернетка → правки автора → коміт прийняття автором (`docs(spec): прийняти …`). Прийняту
spec не редагують; будь-яка зміна — нова spec-fix.
